## 0. The user's fence, and how it is enforced rather than promised

> *"เฉพาะ bantamkit + ตัวเลขล้วน"* — bantamkit only, numbers only.

1. **bantamkit transcripts only.** Every other project under `~/.claude/projects/` is out
   of scope, not deprioritised.
2. **Committed artifacts carry numbers and statistics only.** No transcript excerpt, no
   prompt text, no filename from any project.

Fence 2 is a check, not an assurance. `transcript_id` is
`sha256(<path relative to the transcript root>)[:16]`, and `fence_violations()` re-reads
the **rendered artifact** and fails the run if any string anywhere in any row — key, value
or nested value — contains a path separator, a `.jsonl` suffix or a home-directory prefix.

**It fired on this program's own first draft.** The draft committed a
`git_branches_recorded` column; a branch name carries a `/`, and more to the point a branch
name is neither a number nor a statistic. The column is now
`git_branches_recorded_count`. The fence found that in the artifact rather than in a
review, which is the only reason to make a fence mechanical.

## 1. The selection rule, and why there is a cutoff

### 1.1 In scope: a transcript whose every recorded `cwd` is inside the bantamkit repo

The rule is on the **recorded working directory**, not on the name of the directory the
host filed the transcript under. That distinction is not pedantic — see §7.1, where it
turns out to select 207 transcripts rather than 11.

- **PURE** — every `cwd`-bearing line under the cutoff has `cwd` equal to the bantamkit
  repo root or below it. **In the corpus.**
- **MIXED** — some lines are bantamkit and some are another project root. **Excluded**,
  §2 E2.
- **OUTSIDE** — no bantamkit line at all. **Excluded**, §2 E1.

### 1.2 Every number is a function of the lines timestamped before `2026-08-17T16:29:52Z`

That instant is the commit of the pre-registered bar (`f48335c`, 2026-08-17T23:29:52+07:00).
Two reasons, and the second is the one that matters:

1. **The corpus is exactly what was already recorded when the bar was frozen.** The bar's
   §0 claim 1 — that no transcript was opened to write it — cannot be falsified
   retroactively by U3's reads, because nothing U3 caused to be recorded is in the corpus.
2. **The numbers are append-only-stable, so the reproduction check does not have to be
   made green by regenerating the evidence.** `~/.claude/projects/` is a live directory:
   the user's next session appends to it, and this job's own session was appending to it
   while this was written — its transcript carried **727** assistant lines at the cutoff and
   **756** within a quarter of an hour after it. A statistic over "the directory as it is"
   is false by tomorrow. Under the cutoff, a new session, a resumed session and this unit's own
   transcript all land after it and **cannot move a committed row**.

The cutoff **truncates the input**, it does not merely filter files, so a session that is
resumed later still reproduces its committed row. A transcript that straddles the cutoff
is carried truncated and flagged `truncated_at_cutoff` — 2 of the 207 are. Dropping them
would make the corpus depend on when a session happened to end.

## 3. The corpus, as numbers

### 3.1 `model_calls`, derived properly, and the divergence stated as a number

The bar quotes `[prior]` at its §0 claim 5: **8 transcripts / 1,596 assistant turns /
median 166 / min 117 / max 467**, from counting lines containing `"type":"assistant"`, and
labels it a line-level approximation with no threshold depending on it. It is not a
model-call count, and here is by how much.

**A Claude Code transcript writes one line per content block.** A reply carrying a thinking
block and three `tool_use` blocks is four lines with the same `message.id`, the same
`requestId` and the same prompt-token figures repeated verbatim on each.

| | committed corpus (n=207) | the bar's own directory (n=11) |
|---|---|---|
| assistant **lines** — the approximation | **16,241** | 2,284 |
| **`model_calls`** — distinct `requestId`, non-synthetic | **7,895** | 1,149 |
| `model_calls` — distinct `message.id`, independently | **7,895** | — |
| the two derivations agree | **yes, exactly** | — |
| synthetic assistant lines (host error notices, not calls) | 4 | — |
| **divergence, lines − calls** | **+8,346** | +1,135 |
| **divergence, lines ÷ calls** | **2.0571×** | 1.9878× |
| **the approximation overstates model calls by** | **105.71%** | 98.78% |

Per transcript, `model_calls`: **min 6, p25 13, median 26, p75 53, max 326**, Σ 7,895.
Per transcript, assistant lines: min 13, p25 34, median 63, p75 103, max 727.
Lines per call, per transcript: min 1.551, median 2.217, max 3.500.

**The divergence is reported, not reconciled.** The bar's 1,596 was a snapshot of a smaller
set at an earlier moment and its exact moment is not recorded, so the proper count *for
that snapshot* cannot be recovered. What can be said exactly: on the same directory, under
the cutoff, the same line-level method gives 2,284 where the proper count is 1,149. Divided
by this corpus's own ratio, 1,596 assistant lines correspond to roughly **776** model calls.
That figure is an inference and is marked as one; 7,895 and 1,149 are measurements.

**A second-order consequence worth more than the first.** The prompt-token fields are
repeated verbatim on every line of a reply too, so **summing recorded usage over lines
inflates the token totals by the same ~2.06×**. And `output_tokens` is worse than repeated:
it is a *streaming* value — the lines of one real reply carry 3, 3, 3, 2478 — so reading it
off the first line under-counts a message by more than an order of magnitude. The first
draft of the survey did exactly that and reported the corpus's output tokens as 1,507,030
instead of **6,137,772**, a 4.07× under-count, visible only because it made
`bytes_per_output_token` read 17.6 B/token. Both are now accounted once per `message.id`,
by the maximum over the message's lines.

### 3.2 The token factor, MEASURED from recorded usage. The fallback is NOT taken

Bar §10.3 refuses the mechanism's own `Math.ceil(text.length / 4)` and requires bytes times
a factor **measured from the corpus's own recorded usage**, with an UNMEASURED-IN-TOKENS
fallback at §10.3(4):760 if the recordings do not carry usage.

**They do. All 207 transcripts carry per-call usage, so the fallback is not taken.**

**The fields used, named exactly as §10.3(2):752 requires.** The recorded prompt is
`message.usage.input_tokens` **+** `cache_creation_input_tokens` **+**
`cache_read_input_tokens` — the three fields the whole prompt is partitioned across under
prompt caching. This is not a detail: over the corpus, `input_tokens` alone sums to
**68,503** against a prompt sum of **793,611,304**, so reading "the recorded input-token
figure" as the field literally named `input_tokens` would be wrong by a factor of
**11,585**. See §7.3.

**How the factor is measured.** Within one transcript the prompt grows by append, so across
its calls `recorded_prompt_tokens(i) = fixed_cost + bytes_before(i) / bpt` is a straight
line, and ordinary least squares recovers both unknowns. The fit stops at a transcript's
first host-level compaction boundary, because a boundary breaks the append-only premise.
Restricted to `message.content` bytes — the byte definition a replay reconstruction will
actually produce:

| statistic | min | p25 | median | p75 | max |
|---|---|---|---|---|---|
| **`bytes_per_prompt_token`** | 1.1220 | 1.6889 | **1.8284** | 2.0097 | 2.8229 |
| fit `r²` | 0.892118 | 0.986020 | **0.992268** | 0.995754 | 0.999219 |
| fit intercept, tokens | 4,545.2 | 20,965.7 | **25,350.2** | 27,011.8 | 50,385.1 |
| intercept-free incremental median | 0.6249 | 1.5871 | **1.7734** | 1.9577 | 2.6629 |

**Three derivations, and where they agree.** The fitted slope (1.8284) and the
intercept-free per-call difference median (1.7734) — which assumes nothing about the fixed
cost — agree to within **3.0%**. `r²` is 0.99 at the median, so the linear model is not
being forced.

**The fixed cost the transcripts do not contain.** The intercept is the system prompt, the
tool schemas and the project instructions: billed on every call, present in no transcript.
It is corroborated independently by a first-call bound that uses only call 1 and the
intercept-free factor — median **26,516 tokens** against the fitted **25,350**, **4.6%**
apart, neither derived from the other. **U4's reconstruction cannot produce those tokens
and must either add them as a declared constant or report without them and say so.**

**A hypothesis this survey held and then refuted.** The first draft fitted `payload` bytes
(message content **plus** host-injected attachments) and expected the two byte definitions
to bracket the factor from above and below. They do not: the two fitted slopes agree to
four decimal places at the median (1.8284 against 1.8289) and the **entire** difference
lands in the intercept, which moves by about 30,000 tokens and goes negative (median
−5,239.1, min −35,502.0). So the attachment bytes are a near-constant offset — injected
once, not re-sent — and the byte definition is nearly irrelevant to the **factor** while
being decisive for the **fixed cost**. Both fits stay committed, because that agreement is
the evidence, and a survey that kept only the definition it preferred could not show it.
The negative intercept is left signed and unclamped: it measures that serialised attachment
bytes over-count the wire.

**An independent second estimate, not blended into the first.** An assistant message's own
content bytes over its own recorded `output_tokens`, same call, no fit and no prefix:
median **1.4776** B/token (min 0.3805, p25 1.1247, p75 1.8163, max 5.1770). It is a
*different* quantity — an output is model prose and code, a prompt is dominated by tool
output — and the two are reported side by side, never averaged.

**And the size of the defect §10.3 exists to avoid.** The mechanism's own estimator assumes
4 B/token on ASCII. This corpus measures 1.8284. So `estimateTokens` **under-counts prompt
tokens by 2.1877×** here. Reported as one measured ratio, not as a correction factor to
apply: the bar's axis is the measured factor, and the mechanism's estimate is never the
axis.

## 5. Reproduction

`--check` regenerates the rows and compares **named columns** matched by `transcript_id`.
What it catches, each verified by mutating a copy rather than asserted:
a changed value; `3` against `3.0`; a `null` becoming a `0`; an undeclared new key; a
committed key deleted from the row; the committed keys reordered among themselves; a
changed row count; and a committed transcript that is no longer in the regenerated corpus.
What it deliberately tolerates: **row order**, which is not a property this artifact
asserts, and a key declared in `ADDITIVE_KEYS_THE_ARTIFACT_PREDATES` — empty at first
commit, so the next added column forces a dated declaration.

**Byte-identity is not attempted, on two independent grounds.** RB-P46: a whole-line
byte-identity check is structurally incompatible with the additive-field convention. And
the corpus is a live directory, so a byte-identical corpus statistic is false the moment
the user opens another session — which is what the cutoff answers and what byte-identity
could not.

**The suite is not evidence (RB-P28).** `runtime-py/tests/test_compaction_corpus_survey.py`
pins the **instrument**: 26 nodes, every one of them over a synthetic fixture directory this
test file wrote. No node reads `~/.claude/projects/`, names a transcript, or asserts any
number in this document — per RB-P14 Gate 2 a node asserting "the corpus has 207
transcripts" is a fact about the world that goes red when the user works tomorrow, and the
cheapest way to green it is to edit committed evidence. The three mutations the nodes exist
to catch are the three defects that were actually found while writing the program, not three
invented ones: counting lines as calls, reading `output_tokens` off the first line of a
message, and letting a non-numeric string into a row.

## 6. Limitations of this corpus, recorded rather than buried

1. **206 of 207 transcripts are sidechains, not sessions.** A subagent transcript is a
   real recorded agent run with real prefix growth and real recorded usage, and it is a
   legitimate replay target. It is **not** a human-driven session, its trajectory was set
   by a brief, and it is short: median 26 model calls. Nothing measured on this corpus
   generalises to a long interactive session.
2. **The one session is truncated and is this job's own.** The corpus's only top-level
   session is the session that ran this job, cut at the bar's commit. It is also the only
   transcript carrying host-level compaction, and the largest by every byte and token
   column. Any per-transcript figure it dominates should be reported with it named.
3. **Independence is weaker than the transcript count suggests.** 196 of the sidechains are
   subagents of the three sessions excluded by E2, and 10 are subagents of the session in
   §6(2). Sidechains under one parent share that parent's project state, its branch and
   often its brief template. They are not 207 independent draws of anything. Their
   *prefixes* are independent — each was built from its own brief — which is what makes
   them usable, and the distinction matters for any statistic quoted with an *n*.
4. **Three Claude Code schema generations.** `2.1.222`, `2.1.224`, `2.1.226`. The
   `output_tokens` streaming behaviour was observed in the oldest and the block-per-line
   layout in all three, but no claim is made that the schemas are otherwise identical.
5. **The corpus is a snapshot of a live directory.** The cutoff makes it reproducible; it
   does not make it representative of the user's work after 2026-08-17.
6. **`attachment_bytes` is a declared over-estimate.** It is an attachment's serialised
   JSON length, which includes keys the wire does not carry, and §3.2 measures that it
   behaves as a near-constant offset rather than as re-sent content.

## 7. Escalations — measured here, bearing on the committed bar, NOT edited

Filed rather than fixed. The bar predates every number above and §10 of it is frozen.

### 7.1 The bar's `n=8` is not the corpus the user's own fence selects

The bar's §2.2:217-228 builds an explicit statistical argument on `n=8` at the transcript
grain — that pooling 1,596 turns would report `n=1596` for a quantity with 8 independent
realisations — and §11(2) requires "all eight per-transcript figures printed beside every
median."

**Under the fence as the user stated it, the corpus is 207 transcripts, not 8.** The reason
the two differ is mechanical: Claude Code keys its project directory by the cwd the session
was **launched** from, not the cwd it worked in. **211** files on this machine have a recorded `cwd` inside the
bantamkit repo: **12** under the bantamkit-named project directory and **199** under a
directory keyed to the user's home, because those sessions were launched from there. Under
this cutoff that is 11 and 196 in the corpus, plus the 3 excluded by E2. A selection rule of
"the bantamkit-named directory" — which is what produces 8, or 11 under this cutoff —
silently discards **94.7%** of the bantamkit transcripts on this machine.

U4 cannot satisfy "print all eight" against 207 rows. **This is a question for the user, not
a number for U3 to shrink to fit.** Sub-sampling would be the obvious accommodation and it
is deliberately not done here: the rows are committed sorted by `transcript_id`, a hash
order that cannot be result-informed, so a later unit can take a declared prefix of the
corpus as a sample **with a dated declaration** and the choice stays auditable.

The §2.2 *argument* survives intact and is worth keeping: turns within a session are not
independent observations of a path integral over that session. What does not survive is the
number 8.

### 7.2 §10.2's threshold has two readings that differ by orders of magnitude

§10.2:719 puts boundary *k* at "the first call index at which B0's **cumulative prefix**
reaches `k · T`", and §10.2:723 sets `T` = `COMPACTION_PROACTIVE_PCT` percent of
`COMPACTION_TOKEN_BUDGET` = **76,800** tokens (source constants at §10.1:705-706).

But `COMPACTION_TOKEN_BUDGET` is a **live-window** budget and `proactivePct` is the fraction
of that window at which the mechanism itself acts. Applying a window fraction to a
**cumulative** sum is a category error, and on this corpus the two readings are not close:

| reading | statistic | min | p25 | median | p75 | max |
|---|---|---|---|---|---|---|
| **A** — `T` as live-window occupancy (the mechanism's own meaning) | peak prompt tokens ÷ T | 0.3430 | 0.7313 | **0.9739** | 1.6266 | 5.3022 |
| **B** — `T` as cumulative re-send (§10.2 as written) | Σ prompt tokens ÷ T | 2.70 | 8.31 | **17.98** | 52.38 | 778.61 |

Under **A**, 102 of 207 transcripts ever reach `T` and **105 are UNINFORMATIVE under U-2**
before any arm runs. Under **B**, the median transcript gets **18 boundaries** across 26
model calls — a summarizer boundary roughly every 1.4 calls, on a session whose live window
never reached the threshold that was supposed to trigger it.

Both readings are honest readings of the committed text. **U3 does not choose**, applies
neither, and reports both, because §10.2 also carries a standing refusal to re-tune `T`
after seeing that nothing fired — and picking the reading under which more fires would be
that refusal defeated by interpretation instead of by edit.

### 7.3 §10.3(2)'s "the recorded input-token figure" has a wrong literal reading

§10.3(2):752 defines the factor as reconstructed prefix bytes "÷ **the recorded input-token
figure** at the same call". Claude Code records four token fields, and the one literally
named `input_tokens` is the **uncached remainder**: over this corpus it sums to 68,503
against a true prompt sum of 793,611,304, a factor of **11,585**. §10.3(2) does require U3
to name exactly which fields it uses, which is the clause working as intended — this is
recorded so that no later unit reads the phrase literally and produces a factor four orders
of magnitude wrong.

### 7.4 U-4's verdict is grain-dependent, and the bar has a rule for that

`host_precompacted_boundaries` is non-zero on 1 of 207 transcripts, so **U-4 as written does
not fire**. But that one transcript is the corpus's only session and its largest member by
every byte and token column, so any **pooled** figure — the pooled sum the bar requires
beside every median at §2.4 — is dominated by the one transcript whose headroom was already
truncated by a mechanism this job is not measuring.

The bar's own rule for a verdict that depends on the grain is §3.1: *"a pair whose verdict
differs between the two grains is not decided by choosing a grain: the run stops and the
question is escalated."* That rule is written for the floor test. It is flagged here because
U-4 has the same shape, and U4 should not discover it at reporting time.

### 7.5 The corpus contains the job that is measuring it

The single session in this corpus is the session that wrote the bar and is running this
job. Its content includes the pre-registration itself. Nothing about a byte or token count
is invalidated by that. What it does mean: a summary quality judgement made on that
transcript would be a mechanism summarising its own grading rules, and the fidelity axis of
§3.2 extracts anchors from the transcript's own text. Recorded so the option of excluding it
stays available to U4 as a **declared** choice rather than an oversight.

### Amendment 1 — 2026-08-18. Two of the 44 columns are not cutoff-restricted, declared

**What happened.** About forty minutes after this artifact was committed, `--check` went
**RED on the pristine committed `.jsonl`, with nothing modified.** §1.2 above claims every
number is a function of the lines under the cutoff. That claim was true of **42** of the 44
columns and false of two:

| column | committed | regenerated ~40 min later |
|---|---|---|
| `lines_total` (row 50) | 2,432 | 2,508 |
| `untimestamped_lines_by_type` (row 50) | mode 133, permission-mode 133, last-prompt 133, ai-title 132, file-history-snapshot 13 | 137 / 137 / 137 / 136 / 13 |

Row 50 is the corpus's single live session — the one §6(2) already flags as this job's own.
Both columns count lines **without** applying the cutoff, so they move every time anything
is appended to an open transcript. This is precisely the failure mode §1.2 and §5 name, and
it was missed on two columns while being got right on forty-two.

**What was done, and what deliberately was not.**

- The committed `.jsonl` is **not regenerated and not retro-edited.** Its values were true
  at the cutoff and they stay. That is the invariant, and the alternative — regenerating
  evidence to green a check — is the thing the check exists to prevent.
- `--check` now skips the **value** comparison for exactly the two columns enumerated in a
  dated declaration, `LIVE_COLUMNS_EXEMPT_FROM_THE_REPRODUCTION_CHECK` in the survey
  program. **Nothing is generically lenient.** The exemption is by NAME; the key-set check
  runs first, so an exempt column must still be present on both sides; and the drift is
  **printed** on every run, whether the verdict passes or not — an exemption from failing,
  never an exemption from being reported. A rule of "skip a column that differs" would be
  tolerance stated over a set and would pass every mutation the comparator exists to catch.
- Nine nodes were added to guard the repair against becoming the disease. The load-bearing
  ones: the cutoff-restricted **neighbour** `lines_under_cutoff` still fails; a plausible
  undeclared sibling name still fails; a declared-live column **deleted** from the row still
  fails; and emptying the declaration brings the original red straight back.

**Which is inherently live and which was computed at the wrong scope** — the distinction
that says whether the declaration is permanent or a wart:

- **`lines_total` is a WART.** It was computed at the wrong scope, not inherently live: its
  cutoff-restricted counterpart `lines_under_cutoff` was already committed in the very next
  column. It should have been cutoff-restricted from the start, and on this evidence it
  should not have been a committed column at all — "lines on disk" is a property of a file
  at an instant, not of a corpus. **A later artifact should carry `lines_under_cutoff` and
  drop it.**
- **`untimestamped_lines_by_type` is INHERENTLY LIVE under the cutoff rule as declared**,
  which is that a line enters a statistic iff *its timestamp* is under the cutoff — and
  these lines have none. A repair exists and is named rather than applied: a line's
  **position** orders it, so an untimestamped line could be counted iff it precedes the
  first line whose timestamp is at or after the cutoff, which is append-stable. Applying it
  now would change the regenerated value and force a retro-edit of committed evidence. So
  the repair belongs to the **next** artifact's cutoff, and the column stays exempt in this
  one.

**One latent drift was found by reading rather than by waiting, and FIXED rather than
declared.** The `UNPARSEABLE` and `NOT_AN_OBJECT` counters were incremented before the
cutoff guard, so a future malformed line would have drifted `line_types` — a **checked**
column, a second time bomb of the same kind. They now land in the declared-live dict. No
committed row carries either key, so no committed value changed.

**`truncated_at_cutoff` is deliberately NOT exempt.** It is cutoff-derived and stable under
append. The one event that would move it — a corpus member being **resumed** — is a change
of character in the evidence that *should* turn the check red and be answered with a dated
amendment, which is this mechanism working rather than failing.
