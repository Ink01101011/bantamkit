# AS-4's gate: naming already wins

J46-19, job46. `docs/roadmap-agent-stack.md` AS-4 attaches a gate to lexical retrieval over
a document corpus:

> **Gate:** measure discovery precision on the real corpus first — `project-real-corpus-denominator`
> and `reader-verified-over-365924-files` already name the denominator. **If naming the file
> directly already wins, say so and stop.**

**VERDICT: GATE FAILS.** On this machine's real work, naming the file directly opens it in a
median of **2 tool calls** and never once used a search tool, while a lexical ranker's
recall over the same corpus is bounded above at **48.3%** — and reaches only **18.9%** of
real discovery queries end to end, because 60.8% of them target a file that is not in the
corpus at all. AS-4 is refuted on this corpus. J46-20, J46-21 and J46-22 are dropped. AS-5
(embeddings) stays gated behind an AS-4 that never shipped, which is the correct state.

**The filename records when this unit was planned (2026-09-10), not when it ran.** Every
number below was measured **2026-09-11** at `8b7a8b9`, tree clean. They are dated, not
constant: the transcript corpus and the working tree both grow with every session.

## Nothing was built

No retriever, no scorer, no index — the thing the gate exists to authorise was not written
in order to authorise itself. The measurement is possible without one because of a property
of BM25 and of every lexical ranker in its family:

> A lexical ranker assigns a non-zero score only to documents sharing **at least one query
> term**. So `grep -l` for the union of a query's terms returns **exactly** the ranker's
> non-zero-score set. Its recall is therefore an **upper bound on that ranker's recall at
> any k**, and no tuning, no weighting scheme and no choice of k can exceed it.

If the bound is low, AS-4 is refuted with no prototype. It is low.

The probe beside this file — `2026-09-10-job46-as4-probe.py` — is the whole measurement and
is rerunnable:

```
.venv/bin/python docs/eval-data/2026-09-10-job46-as4-probe.py <transcript-dir>
```

Nothing mutated the user's transcripts or memory store. The 28 transcripts were copied with
`cp -Rp` into a scratch directory and every read was against the copy.

## The pre-registered query set

The set was fixed by a **rule**, before any score existed, and the rule was chosen so that
no question could be written to be won: **the queries are the user's own prompts, and the
right answer is chosen by the transcript rather than by the author of this file.**

1. **Source.** The 28 Claude Code transcripts for this project, copied read-only:
   **38,516 records**, 80 MB of JSONL.
2. **A candidate** is a user turn that is genuinely user-typed: `type == "user"`, not
   `isMeta`, not a `tool_result`, with `<system-reminder>`, `<command-*>`,
   `<task-notification>`, `<local-command-*>`, `<user-prompt-submit-hook>` and
   `<bash-stdout|stderr|input>` blocks stripped, non-empty after stripping, and not a
   compaction-resume preamble. **787 user turns → 261 user-typed prompts.**
3. **A candidate is a discovery query** iff, before the next user turn, the assistant opened
   a concrete file — `Read`, `Edit`, `Write`, or a Bash reader (`cat`, `sed -n`, `head`,
   `tail`, `less`). **That first file is the ground-truth target.**
   **261 → 148 discovery queries.**
4. **Every one of them is used.** No sampling, no exclusion of hard cases, no hand-picking.

**The query set is not committed.** It is 148 verbatim prompts from the user's private
transcripts, and this repo is public; publishing them to prove a point about retrieval would
be a worse trade than losing the verbatim record. The extraction rule above is deterministic
and the script implements it, so a reader reruns the derivation against their own transcripts
rather than reading a copy of the user's. The two prompts quoted below are ones the repo
already publishes (`runtime-py/src/bantamkit/memory/store.py`, `docs/roadmap-agent-stack.md`).

**96.6% of the set — 143 of 148 — contains Thai.** That is not a design choice; it is what
the population is. An all-English query set would have described a user who does not exist.

## Arm N — the baseline: naming the file directly

Defined before measuring, and measured from behaviour rather than from a re-enactment: for
each of the 148 discovery queries, **how many tool calls did the agent spend between the
prompt and opening the target file?** This is the arm AS-4 has to beat.

| | measured |
| --- | --- |
| tool calls from prompt to opening the file | **median 2**, mean 3.12, min 1, max 12 |
| opened on the **first** tool call | **38/148 = 25.7%** |
| opened within 3 calls | **65.5%** |
| queries where the agent used `Grep` or `Glob` at all | **0 of 148** |

The last row is the finding. **Not once in 148 real discovery queries did the agent search
for the file.** It went to a path it already held — from the brief, from the roadmap, from
the checkpoint, from the previous turn. Ranking is being proposed as a faster route to a
destination the agent is already standing on.

Only **1 of the 58** in-corpus queries contains the target's basename, so the user is not
naming the file either. The path comes from the *task context*, which is the thing a lexical
ranker does not have and cannot acquire.

**A limitation, stated plainly:** the ground truth is "the file the agent opened first",
which assumes the agent was right. If it was wrong, that pair is mislabelled. The bias is
symmetric — Arm R's ceiling is scored against the same labels — but it does flatter Arm N's
*cost*, because calls spent on a wrong file before the right one are not counted. The 48.3%
ceiling below does not depend on the cost figure.

## Arm R — the ceiling, with nothing built

`grep -l` over C1 for the union of each query's terms, tokenised with `memory_recall`'s own
`_tokens()` — `re.findall(r"[a-z0-9]+", text.lower())`, the tokenizer AS-4 would inherit —
minus a 20-word English stoplist and tokens shorter than 2 characters.

| | measured over the 58 in-corpus queries |
| --- | --- |
| **grep-any-term recall — UPPER BOUND on any lexical ranker at any k** | **28/58 = 48.3%** |
| queries tokenising to the **empty set** (recall 0 by construction) | **18/58 = 31.0%** |
| ASCII tokens per query | **median 2** |
| candidate set on the hits | **median 554 files = 26.9% of C1**; max 1,974 = 95.9% |
| **end to end** (28 of all 148 discovery queries) | **18.9%** |

Read the last two rows together. In the best case AS-4 can reach — the 48.3% where the
target is in the candidate set at all — the ranker must lift the right document out of a
**median of 554 candidates using a median of 2 query tokens**, against a baseline that
opens it in 2 tool calls with no search. There is no margin there to win by.

The 18 empty-set queries are the ones a Thai speaker actually types:

> `ทำต่อ` · `แก้ต่อเลย` · `มีงานค้างอะไรเหลือบ้าง` · `เอาข้อ 1 ต่อเลย` · `ภาพรวมเป็นยังไง`

Every one has a real, unambiguous target in the tree. Every one scores 0 against every
document under the tokenizer AS-4 would inherit.

**Sensitivity.** Dropping the stoplist and admitting 1-character tokens raises recall to
**39/58 = 67.2%** and empty-set queries fall to 10 — but the median candidate set on the
hits rises to **717 = 34.9% of C1** (measured at C1 = 2,056, before this file and its probe
were added). The gain is bought entirely by bare digits (`4`, `5`,
`7`) matching most of the tree. The honest band is **48.3%–67.2%, and the higher figure is
worse retrieval**, not better.

## The Thai result, reported separately

This is the most important sentence in the unit, and it holds whichever way the gate falls.

**A better tokenizer does not rescue AS-4, because there is nothing on the other side to
match.** AS-4 could plausibly fix `memory_recall`'s ASCII-only tokenizer. So the ceiling was
re-measured against the *content words themselves*, script-agnostically: for each in-corpus
query, do any of its Thai character runs (≥3 chars) appear anywhere in its target file?

| | measured |
| --- | --- |
| in-corpus queries carrying a Thai run ≥3 chars | **58 of 58 — all of them** |
| ... whose **target file** contains any of those runs | **1 (1.7%)** |
| ... matched by **any** file in C1 | 34 (58.6%) |
| C1 files containing any Thai codepoint at all | **113 of 2,058 = 5.5%** |

**The queries are in Thai and the corpus is in English.** A perfect Unicode-aware tokenizer,
correctly segmenting Thai (which has no word boundaries, so this is itself unsolved without
a dictionary and would be a new runtime dependency the job forbids), would have a recall
ceiling of **1.7%** on the query's actual content words. The ASCII tokenizer is not the
bottleneck — it is a symptom. The bottleneck is that **lexical retrieval requires the query
and the document to share a vocabulary, and for this operator they never do.**

That gap is a cross-lingual one, and cross-lingual matching is the thing embeddings are for
— which is AS-5. AS-5's gate says it may start only once AS-4 has shipped and its measured
ceiling is the limiting factor. AS-4 has not shipped and will not, so **AS-5 remains closed**,
and this file is the reason it must not be reopened by pointing at the 1.7%.

## Verdict

**GATE FAILS. Naming already wins.** Arm N opens the right file in a median of 2 tool calls
using zero searches; Arm R's recall over the same corpus cannot exceed 48.3%, reaches 18.9%
of real discovery queries end to end, and must rank the answer out of a median of 554
candidates from a median of 2 tokens — and against the query's real content words, in Thai,
its ceiling is 1.7%.

Consequences, recorded here and amended onto AS-4's row:

- **J46-20, J46-21, J46-22 are dropped.** They implement the refuted thing.
- **AS-5 stays gated** behind an AS-4 that never shipped.
- **`memory_recall`'s scorer was not touched**, per the unit's scope.

## One correction, recorded rather than quietly fixed

The first run of this probe reported every candidate set as 2,030–2,043 files regardless of
the query — a number identical for `pypi` and for `bantamkit`, which is not a property any
corpus has. The cause was in the probe, not the corpus: the invocation was
`grep -lieE "<pattern>" -- <files>`, and `-lieE` parses as `-l -i -e E`, making **`E` the
pattern** and the intended pattern the first filename. Every file containing the letter `E`
matched. Corrected to `grep -l -i -E`, per-token document frequency separates properly
(`publish` 50, `pypi` 36, `merge` 223, `mcp` 382, `memory` 637, `bantamkit` 802 of 2,058)
and recall fell from an apparent 69.0% to the real **48.3%**.

The uncorrected figure would have made AS-4 look *better* than it is, which is the direction
a measurement's own bugs are least likely to be caught in. It was caught by the fact that
`pypi` and `bantamkit` returned the same count — a spot-check of a number that had no
business being equal.

**`test_encoding_gate.py` found a real defect in the probe and it was fixed, not silenced.**
The first draft called `subprocess.run(..., text=True)` with no `encoding=`, which decodes
with the platform locale — on Windows that is cp1252, and this probe's entire subject is
Thai text. Now `encoding="utf-8", errors="replace"` at both call sites. A measurement about
non-Latin retrieval that mangled non-Latin bytes on half its platforms would have been the
same class of error as the `-lieE` bug above, caught by a gate instead of by a spot-check.
