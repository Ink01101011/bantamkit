# M1 — pre-registered screen for non-fragile `critique` cells

**Job:** `nonfragile-bar-cells`, unit M1. **Layer:** Measurement.
**Branch:** `feat/nonfragile-bar-cells` off `b44793e` (v0.15.0).
**Written:** 2026-08-12, **before any arm ran.** Nothing below was edited after
the first request went out; results live in the unit report and in
`docs/eval-data/`, not here.

## 0. What this screen is for

The perturbation bar (RB-P14) reports `fragile: true` for the only cell the
project has been using — `task-completion` / `qwen2.5:14b-instruct` /
`nav-prod-port`, 1/12, 4/12, 3/12 of its own meaning-preserving family. The
crediting rule in `docs/eval.md` forbids crediting a rubric edit until the bar
reports a cell non-fragile, so no rubric work is currently measurable. This
screen looks for cells where it would be.

Two kinds are wanted, and both are reported:

- **Defect bar** — non-fragile, and the critic is *wrong* on it.
- **No-regression anchor** — non-fragile, and the critic is *right* on it.

"No non-fragile cell exists" is an admissible result and will be reported with
its numbers if that is what comes out.

## 1. Definitions, fixed in advance

- **Cell** = (critic model, task, repeat/seed, answer bytes). The answer is
  replayed byte-exact from a transcript; the bar never re-runs the answerer.
- **Threshold** T = 7 (`assets/rubrics/task-completion.yaml`).
- **Fragile** = family `score_min < T <= score_max` (`criticreplay._family_stats`).
  A point passes iff every replay of it scores ≥ T. Therefore **non-fragile ⟺
  family pass rate is exactly `0/F` or `F/F`** — there is no third case, and
  that identity is what makes the two kinds below exhaustive.
- **Answer correct** = the frozen suite's own scorer, `evalrun.score_output`,
  as recorded in the transcript's `passed` field. Not my judgement.
- **Classification of a non-fragile cell:**

  | | answer correct | answer incorrect |
  |---|---|---|
  | pass rate `F/F` | **anchor** (critic right to accept) | **defect bar, false-accept** |
  | pass rate `0/F` | **defect bar, RB-P4 shape** (critic wrong to reject) | **anchor** (critic right to reject) |

## 2. Candidate cells, and why those

### 2.1 Rubric variant: as-filed only

Fragility is a property of *one* variant's family, so the screen needs only the
rubric as filed — ~16 requests per cell, not the 96 a two-variant attribution
check costs. `HEAD:assets/rubrics/task-completion.yaml` has blob
`ab8886fe1ce62c3a9e2331469a48b7e471414b5e`, **byte-identical to
`d2f78b7:` — i.e. the spec's `A-asfiled`** (the round-2 edit was withdrawn).
That gives the screen a free Gate 0: the 14b `nav-prod-port` identity scores
must reproduce `5, 5, 5` from
`docs/eval-data/2026-08-11-sa3-14b-nav-prod-port-critic-replay.json`. If they
do not, the screen is mis-assembled and every other number in it is void.

### 2.2 Answer provenance: `bare`, not `critique` — and this is load-bearing

The brief says "screen the `critique` config". The critic under screen is
`task-completion`, which is exactly what the `critique` config gates with. But
the *cells* cannot come from `critique`-config transcripts, for a structural
reason found while designing this screen:

> When the `critique` gate exhausts its rounds, `agent.run` raises, `output`
> stays `None` (`evalrun.py:535-560`), the transcript records `"output": null`,
> and `criticreplay.load_cases` skips it (`criticreplay.py:419`).

So **a `critique`-config transcript can never contain an answer the critic
rejected.** Screening `critique` transcripts would make the RB-P4 shape —
critic robustly rejects a correct answer — structurally unreachable, because the
only evidence of it is deleted by the config that produces it. 14b
`nav-prod-port` is the proof: `critique` scores `XXX` (exhausted, no answer
recorded) while `bare` on the same model, task and seeds scores `PPP` — a
correct answer, recorded.

The screen therefore takes answers from `--config bare`, which attaches the same
task tools under the same pinned seed and no gate, and replays the
`task-completion` critic over them. The screened object is the critic; `bare` is
the way to hand it every answer, including the ones `critique` throws away.
**Stated as a limitation:** a `bare` answer is the un-gated first answer, so
these cells are the critic's round-0 decision. Cells where the critic revised an
answer across rounds are out of scope for this screen.

### 2.3 Models: `qwen2.5:14b-instruct` and `qwen3:4b-instruct`

- **14b** is where RB-P4 lives. If no cell there is non-fragile, RB-P4 is not
  measurable regardless of what other models do, so 14b gets the full pool and
  the bigger stage-2 cap.
- **4b** is the second model because it is the cheapest answerer in the rack
  (18,809 tokens for the whole `bare` suite against 14b's 26,824, measured in
  `2026-08-10-rebaseline-4b.jsonl`), it produces the most correct answers of the
  three small models (9 tasks at `PPP` under `bare`), and it is a different model
  *generation* (qwen3 vs qwen2.5), so a finding that holds on both is not purely
  a size knob.
- **`llama3.2:3b` and `qwen2.5:7b-instruct` are not screened.** Named here so
  the coverage claim is not read as exhaustive.

### 2.4 Task pool: all 22, both models

The whole frozen suite, 3 repeats each = **66 cells per model, 132 cells total.**
Stage 1 is 1 request per cell, so full-suite coverage at that stage is affordable
and is worth more than a hand-picked subset: it lets the pre-screen heuristic be
scored over the entire identity-score range rather than over cells chosen because
I expected them to be interesting.

## 3. Stage structure

### Stage 0 — transcripts (the answerer; the expensive half)

`evalrun --config bare --repeats 3 --transcripts <dir>` per model, all 22 tasks.
Seeds are `evalrun._seed(model, task, repeat)` and are recorded per transcript.
Nothing under `assets/evals/tasks/` is touched. Transcripts are committed so
every cell's answer bytes trace to a file.

### Stage 1 — identity pre-screen, 1 request per cell

`criticreplay --identity-only --identity-replays 1` over all 66 cells per model.

**Deviation from the brief, declared:** the brief costs `--identity-only` at 5
requests per cell. I run it at **1**, because the committed evidence for
within-cell identity spread is zero — five replays × three cells in the
acceptance run, and `2026-08-12-pb14-14b-nav-prod-port-replay3.jsonl` extends
that to 69 points at R=3 with zero within-point spread. Stage 1 only has to
produce a *promotion* decision. The real identity number is re-measured at
`--identity-replays 5` inside stage 2, which makes the deviation self-checking:
**every stage-2 cell's five identity replays must equal its stage-1 score.** Any
disagreement is reported, and would retire the R=1 pre-screen.

### Stage 2 — the full family, 16 requests per cell

`criticreplay` at defaults (`--replays 1`, `--identity-replays 5`) — F = 12
points, 11 × 1 + 5 = 16 requests per cell — on the promoted cells.

## 4. Promotion rule, fixed in advance

Let `margin = identity_score − 7`. Partition each model's 66 cells:

- **Far-fail (F−)**: score ≤ 4 (`margin ≤ −3`)
- **Far-pass (F+)**: score = 10 (`margin ≥ +3`)
- **Near (N)**: score ∈ {5, 6, 7, 8, 9}

The heuristic under test is *far ⇒ likely non-fragile*. Strata and caps
(14b / 4b), selection deterministic by `(|margin| desc, task asc, repeat asc)`:

| stratum | definition | what it would be | cap 14b | cap 4b |
|---|---|---|---|---|
| **D1** | F− and answer correct | defect bar, RB-P4 shape | 6 | 3 |
| **A1** | F+ and answer correct | anchor (right to accept) | 4 | 2 |
| **A2** | F− and answer incorrect | anchor (right to reject) | 3 | 2 |
| **D2** | F+ and answer incorrect | defect bar, false-accept | 3 | 2 |
| **C** | N (any correctness) | **control** | 4 | 2 |

D1 gets the largest cap because it is the shape RB-P4 needs.

**Control stratum C is not optional and is the point of the exercise.** A
pre-screen that discards good cells is worse than no pre-screen, so near-threshold
cells are promoted too: the two highest-scoring and the two lowest-scoring cells
of N on 14b (one each on 4b), ties broken `(task asc, repeat asc)`. If any control
cell comes back non-fragile, the heuristic leaks and is reported as failed.

**Scoring the heuristic.** A 2×2 of {far, near} × {non-fragile, fragile} per
model, plus the plain statement of how many good cells the far-only filter would
have missed.

## 5. Budget, with the arithmetic

Per-request cost is taken from the §5 amendment of the perturbation-bar spec,
which measured `A-asfiled` at **384 tokens/request** on this exact rubric variant
— the amendment's own instruction is to estimate per variant from a rendered
probe of that variant rather than scale another one. Latency: 1.95 s/request
measured warm on 14b; 4b is **estimated** at 0.8 s/request and that estimate is
scored against actual.

**Stage 0 — answerer.** Budget = the measured `bare` totals for the identical
seeded configuration in the 2026-08-10 re-baseline.

| model | runs | tokens |
|---|---|---|
| 14b | 66 | 26,824 |
| 4b | 66 | 18,809 |
| **total** | **132** | **45,633** |

**Stage 1 — identity pre-screen.** 66 cells × 1 request × 2 models = **132
requests**; 132 × 384 = **50,688 tokens**.

**Stage 2 — full family.** Caps sum to 6+4+3+3+4 = **20 cells on 14b** and
3+2+2+2+2 = **11 cells on 4b**, i.e. ≤ 31 cells × 16 = **496 requests**;
496 × 384 = **190,464 tokens**.

**Total: ≤ 628 critic requests + 132 answerer runs, ≤ 286,785 tokens.**

Wall-clock: 14b (66 + 320) × 1.95 s ≈ 12.5 min; 4b (66 + 176) × 0.8 s ≈ 3.2 min;
answerer ≈ 6 min at an estimated 4 s/run (14b) and 1.5 s/run (4b). **≈ 22 min.**

For scale: RB-P4's round-2 bar cost **264,665 tokens** across four arms to
measure one cell. This screen budgets **286,785** to screen **132 cells** and
fully characterise **≤ 31**.

Every figure above is reported against actual in the unit report, including the
ones I expect to be wrong.

## 6. The manifest's own guards, re-checked per cell (RB-P19)

RB-P19 records that `P3-right-correct` violates the manifest's shared-token
guard — "no added or removed word may appear in the cell's `{task}`" — on
`nav-prod-port`, whose prompt contains *right*. That guard is task-dependent, so
I re-derived it offline for **every** point with a lexical edit and **all 22
tasks**, by word-set symmetric difference against each task prompt. Result,
fixed before any run:

| point | symmetric difference | violates on |
|---|---|---|
| `P1-reviewer-relative` | `checking` → `who`, `checks` | `recall-oncall`, `recall-oncall-rotation` (*who*) |
| `P2-asks-requests` | + `requests` | `recall-org-quota` (*requests*) |
| `P3-right-correct` | − `right` | `nav-prod-port` (*right*) |

**Two of these are new.** RB-P19 names only P3; P1 and P2 violate the same guard
on three further tasks, and nothing in the repo says so. The W and O classes add
and remove no words, so they cannot violate it.

**Handling, pre-registered:** the manifest is **not** edited (a job invariant,
and editing it to improve a result is exactly what is forbidden). For any
screened cell whose task appears above, the report gives the pass rate,
`score_min`/`score_max` and fragility **both with and without** the violating
point, recomputed post-hoc from the committed JSONL rows. Where the two verdicts
differ, the difference is the headline for that cell.

## 7. What this screen cannot conclude

- Nothing about `llama3.2:3b` or `qwen2.5:7b-instruct`.
- Nothing about answers produced under gating (§2.2).
- Nothing about *why* a cell is non-fragile — stability is not validity, and a
  non-fragile cell whose critic is right is still only an anchor.
- `shop-compare` scores by `tool_trace`, so its `passed` is a property of the
  trace, not of the answer text the critic reads. Any `shop-compare` cell that
  reaches stage 2 is reported with that caveat and is not offered as a bar.
- F = 12 on one rubric is not a suite claim about the critic.
