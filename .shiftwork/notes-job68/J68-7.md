## Step 1: tune.py (silver only)

- `tools/eval/recall/tune.py` runs the grid from the plan: 6 x 4 x 4 x 3 = 288 points.
- It scores both views at every point (ruling A+B):
  - A: the bantamkit layers only.
  - B: A plus the `[native]` copy of the row's own project. The project comes from the session, through `$N/session-slug.json`.
    That is the directory the hook's transcript branch hands in.
- The objective is read on B.
- tune.py structurally cannot read gold. `read_silver` refuses any row without `session`, and gold rows have none.
- The selection rule is written into the module docstring before the run. sha256 at the first run: `6865bb87…6228` (`$S/tune.predeclared.sha256`).
  1. Take the highest B recall@3 among the points with B precision@inject >= 0.85.
  2. If no point is feasible: take the highest B precision@inject among the points that meet all three conditions below.
     - B recall@3 >= v1 silver recall@3
     - B Thai > 0
     - >= 10 injections
  3. Ties: higher recall, then higher precision, then the point nearest today's constants.

**Deviation 1 (plan vs code): no `overrides=` argument.** `layered_for_eval` takes none, and adding one would be a
product surface that needs a Node twin. tune.py instead rebinds the module names the scoring walk reads at call time:
`retrieval.GATE_FLOOR`, `retrieval.W_USAGE`, `retrieval.W_TYPE["feedback"]` and `component.RECALL_MIN_SCORE_RATIO` (the
`min_ratio` that `inject_candidates`/`rank_all` pass). It restores them in a `finally`.

**Deviation 2: `score.py --engine v1` no longer measures v1 in this tree.** `score._v1` calls `recall_outcome`, and Task 5
routed that through the v2 scorer. In this tree its "v1" line is the v2 A view at today's constants:
0.0597 / 0.0798 / 0.0833, identical to `current.A`.

- The real v1 comes from the pre-#199 source:
  `git archive 4bab744 runtime-py/src | tar -x -C $S/v1`, then `PYTHONPATH=$S/v1/runtime-py/src .venv/bin/python tools/eval/recall/score.py --engine v1 ...`.
- On silver this reproduces J68-0's baseline-silver.json byte for byte: 0.029850746268656716 / 0.04761904761904762 / 0.04975124378109453.
- My first grid run took its v1 number from `_v1` (kept as `$N/tuning.run1-wrong-v1.json`). tune.py now takes
  `--v1-baseline <file>` (sha256 `d1ad25d1…3e91`), and I reran it.
- **The chosen point is identical in both runs.**
- I left `score.py` unchanged, because its existing test exercises `_engine("v1")`. Making `_v1` refuse in this tree is a follow-up for the orchestrator.

What silver can and cannot see (rerun: the python summary over `$N/tuning.json`, grouping points):

- **No grid point reaches 0.85.** The best B precision anywhere is 0.1049.
- **W_USAGE is inert on silver.** All 4 values give identical A and B metrics at every other triple. The eval's usage ledger is
  `UsageLedger(Path.home(), …)` under a throwaway HOME, so it is empty. Seeding it from transcripts would leak the silver
  labels, which come from the same recall and read events. The tie rule therefore keeps 0.2.
- **GATE_FLOOR is nearly inert.** Real BM25F scores sit well above 3. Only floor 3.0 moves A, by a few injections, and it never moves B.
- **W_TYPE.feedback** changes B in some floor/ratio cells (2 or 3 distinct outcomes) but never beats 1.3 at the top. The tie rule keeps 1.3.
- **GATE_RATIO 0.7** is the only lever. It gives B +0.013 precision for −0.007 recall@3, which is about one positive lost on 70 noisy rows.
