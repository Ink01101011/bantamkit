## What landed (both runtimes)
- `Fact.keywords` is `list[str]` on Python (default `[]`) and `keywords?: string[]` on Node.
  - Read from the frontmatter `keywords` key. An absent key reads as `[]`.
  - Any other shape is refused with `fact '<name>' in <file>: keywords must be a list of strings`. That covers a scalar, `null`, an empty value, a list holding an int, bool or date, a mapping, or a nested list.
  - The check runs after `name`, `description`, `type` and `links` resolve. A file missing one of those still names that problem first, in the same order on both sides.
  - Python: `store.py` `_read_fact`. Node: `store.ts` `readFact`.
- `save(type, name, description, body, links=(), keywords=())`. Each keyword goes through the existing lone-surrogate check, labelled `keywords[i]`.
- The formatter writes `keywords` only when the list is non-empty, after `links`. Python: `_fact_text`. Node: `formatFact`, plus `factOfParsed` for `formatFact(parseFactText(x))`. Python dumps with `allow_unicode=True`, so Thai is written raw. Node's `safeDumpMapping` already writes the same bytes, and no change to it was needed.
- `Memory.save` / `save_outcome` and `saveOutcome` pass `keywords` through.
- MCP: Python `memory_save(..., keywords: list[str] | None = None)`. Node: `pyargs` `opt('keywords', 'listStr')`, and the `memory_save` dispatch in `server.ts`.
- Assets:
  - `assets/tools/memory_save.json` has a `keywords` property, using the plan's text.
  - `assets/skills/memory.md`, which holds the MCP instructions (found with `grep -rln "Write it to match the future recall QUERY" assets`), has the plan's one sentence under "Writing the description".

## The unknown-key property (register (mmmm); Task 6 owns the fix)
This change does not make the unknown-key problem worse. Before it, a hand-written `keywords:` list was an unknown key, and a stamp rewrite dropped it. Now it is an owned key and survives.
A hand-written `keywords` of the wrong shape now refuses the file. Before, the stamp read it and silently dropped it. Now the file is skipped and named by recall, and a save refuses to overwrite it. Fewer bytes are lost than before, not more.
`priority: high` is still dropped by a stamp, exactly as at HEAD. Task 6 owns that fix, and it is not implemented here.

Probe, using a throwaway HOME:
```

```
