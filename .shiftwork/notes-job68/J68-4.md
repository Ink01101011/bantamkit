## Deviations from the plan (code wins, the plan's property is kept)

1. **`LOCK_POLL_MS = 5`, not 10.** The plan's snippet says 10, but the brief says to copy hookadapter exactly, and
   hookadapter has `_LEDGER_LOCK_POLL_MS = 5` (`runtime-py/src/bantamkit/hookadapter.py:393`, `runtime-ts/src/hookadapter.ts:365`).
   Both unit tests pin the equality against hookadapter: Python imports the constants, and Node reads them out of
   `src/hookadapter.ts`.
   `grep -n "_LEDGER_LOCK_.*=" runtime-py/src/bantamkit/hookadapter.py`
2. **`_parse` is strict and reads UTC.** The plan's `datetime.strptime(...).timestamp()` reads a naive datetime as LOCAL
   time, so an age that crosses a DST change drifts by an hour against Node's `Date.parse(...Z)`. It also accepts
   `2026-10-1T0:0:0Z`, a shape `Date.parse` treats differently. Both sides now take `YYYY-MM-DDTHH:MM:SSZ` exactly and
   check every field: Python through `datetime(..., tzinfo=UTC)`, Node field by field plus a leap-year table. Node does
   NOT use `Date.parse`, which accepts `2026-02-29` in a non-leap year. Mutation M10 below shows the difference is live.
   An event with a bad `ts` is a skipped line.
3. **Parity details the plan's snippet did not have.** Each one is reddened by a mutation, listed below:
   - lines are split on `\n` only, never `splitlines()` (M4);
   - Python escapes a lone surrogate as `JSON.stringify` does (M6);
   - Python refuses `NaN` and `Infinity` (M8);
   - Python decodes with `errors="replace"`, because Node's `toString('utf8')` replaces and never throws.
     Invalid UTF-8 inside a kept save line is compared byte for byte after a fold.
4. **A folded weight is written as `%.9f` / `toFixed(9)` text.** `json.dumps(1.0)` gives `1.0`, while
   `JSON.stringify(1)` gives `1`. The two runtimes' shortest-repr output also disagrees on exponents. M5 shows this.
5. **Fold keeps the latest save LINE as it was read** and does not re-serialise it, because a re-encode would respell
   numbers differently on each side. The output order is first appearance of each fact: its `folded` line if it has
   any use, then its latest `save`.
6. **Additive test knobs.** Python takes `UsageLedger(home, store_root, fold_lines=None)`; `None` reads the module
   constant at call time, so the plan's `monkeypatch` test works as written. Node takes
   `new UsageLedger(home, root, {foldLines, lockWaitMs})`, because an ES module constant cannot be monkeypatched. The
   conformance suite uses `fold_lines` / `foldLines` for the auto-fold scenario.
7. **`append` fixes a cut last line.** It reads the prior bytes under the lock. If they do not end in `\n`, it writes a
   `\n` first, so the new event is not glued onto the fragment and lost with it (M7). The fold trigger counts lines from
   those same bytes, so it costs no second read.
8. `fold` on a missing ledger returns at once. Before this fix it spun for the whole 2 s lock wait, because there was no
   directory to take a lock in. The unit test went from 2000 ms to under 1 ms.
9. Node `storeId` copies `os.path.realpath` for a path that does not exist: it resolves the deepest ancestor that exists
   and appends the rest. `realpathSync.native` alone throws `ENOENT` there. Pinned by the conformance cases
   `storeId — a path below the link that does not exist` and `storeId — a Thai name that does not exist`.

## Open questions

- A folded weight at 1e21 or more would make `toFixed(9)` switch to exponent notation, and the two sides' bytes would
  differ. Getting there needs a hand-edited `weight` that large, which a ledger written by bantamkit cannot produce.
  This is not guarded. Should it be clamped?
- The Windows lock and rename path is unmeasured. It is Task 8's manual step, and the suite header says so.
- `last_used` counts a `folded` line's `ts`, which is the fold time, as the plan's snippet does. After a fold, every
  folded fact reads as "used at fold time". Task 5's ranker should know this if it reads `last_used`.
