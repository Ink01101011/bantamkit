## Scope: why "both runtimes" does not apply

`tools/release/publish.sh` is release tooling, not a runtime surface. It adds no CLI flag, MCP tool, error
message or default to either `runtime-py/` or `runtime-ts/`, and neither runtime calls it. So this unit has
no conformance case. The guard is `tools/release/test_version_map.sh`.

## What changed

- `map_pep440_to_semver` maps `aN` to `-alpha.N`, `bN` to `-beta.N` and `rcN` to `-rc.N`. A stable
  version, or anything the mapping does not recognise, passes through unchanged. `npm_dist_tag` returns
  `beta` for any semver containing `-`, and nothing otherwise.
- Phase 0 checks `package.json` and both lock-file fields against the mapped spelling (`NPM_VERSION`).
- Every npm-side use moved to `NPM_VERSION`: registry URL, tarball name, post-publish install, roster
  label, summary URL, and the tag `v$NPM_VERSION`.
- PyPI-side uses keep `VERSION` (PEP 440). That covers the README wheelhouse pin, whose regex now accepts
  an optional `(a|b|rc)N` suffix.
- `npm publish "${NPM_PUBLISH_ARGS[@]}"` is `--access public`, plus `--tag beta` for a prerelease.
- For a prerelease only, phase 0 prints the npm spelling and the exact `npm publish` command. The dry-run
  summary, the confirmation and the `gh release … --prerelease` hint also print only for a prerelease.
- `docs/release-npm.md` has a new subsection, "Prereleases: one version, two spellings, and `--tag beta`",
  and its phase-4 table row now mentions `--tag beta`. The "Version agreement" section is untouched.

## Deviation from the plan

- The plan has the dry run print `npm publish … --tag beta`. In the existing script, a dry run that is
  refused at phase 0 (no `npm whoami`) never reaches the phase-3 summary. So the command is printed in
  phase 0 for prerelease versions, as well as in the dry-run summary. The property is kept: the dry run
  shows the publish command.

## Open questions (for the orchestrator or the user)

1. **The beta cannot pass phase 1 as the tree stands.** On the bumped worktree I ran
   `pytest runtime-py/tests/test_version_agreement.py` and the npm node `the two version declarations
   agree`. Both are red, `'0.37.0-beta.1' != '0.37.0b1'`.
   - They enforce the "one number with two declarations" ruling in `docs/release-npm.md`.
   - The plan does not name them, so I left them unchanged.
   - Teaching them the mapping is a runtime-layer change, and it needs the user's ruling.
   - The same split reaches `build_identity` and serverInfo: Python would report `0.37.0b1` and Node
     `0.37.0-beta.1`.
2. Should `test_version_map.sh` become a gate, for example in phase 1 or under `npm test`? That would add
   a gate to a stable release, so I did not do it.
3. Every prerelease gets the `beta` dist-tag, alpha and rc included, because the plan says so. A `next`
   or `rc` tag would be a choice for the user.
