## #170 — the hook ignored a registration that pins the store via `args`

### Parity, established (the issue says "Not compared")
Both runtimes had the defect: `applyRegistrationStorePin` (hookadapter.ts) and
`_apply_registration_store_pin` (hookadapter.py) read `entry.env` only. Probe (`$S/repro170.mjs`,
the issue's repro adapted: every spelling, distinct session ids so the J64-2 dedupe cannot hide a hit,
throwaway HOME):

    node $S/repro170.mjs $S/base/runtime-ts/dist/cli.js            # HEAD 4bab744 build, Node
    PYTHONPATH=$S/base/runtime-py/src node $S/repro170.mjs x py     # HEAD source, Python

HEAD, both sides identical: `args --store X` -> walk-fact; `args --store=X` -> walk-fact;
`env pin` -> env-fact; `both` -> env-fact (env won; the server lets --store win);
`relative --store rel` -> walk-fact; `empty --store=` -> walk-fact.
After the fix, both sides: args-fact, args-fact, env-fact, args-fact, rel-fact, walk-fact.

### What changed
Both runtimes: a `storeFromArgs` / `_store_from_args` scan of the winning entry's `args` for
`--store X` / `--store=X`; the LAST occurrence decides (argparse keeps the last); an empty value or
a trailing `--store` pins nothing (the server refuses to start on it) and the existing `env` rule
decides. A found X is joined to the session cwd (`path.resolve(cwd, X)` / `os.path.abspath(os.path.join(cwd, X))`)
and fed into the ONE existing resolution (`BANTAMKIT_MEMORY_DIR` on the hook's own process), ahead of
`env`, so `--store` outranks the env pin as it does on the server. `storeScope` names the scope.

Stated limits (also in docs/hooks.md, SessionStart row):
- a missing X: the server designates it, the hook's pin check refuses it (`pinned memory store is
  unreachable ... (BANTAMKIT_MEMORY_DIR=<X>); nothing was created`): `warn` on SessionStart, `error`
  record on UserPromptSubmit, exit 0, nothing created, nothing injected. Probe: `bash $S/missing.sh`
  (both sides: rc=0, SessionStart stdout 420 B profile-only, UPS stdout 0 B, `ls` shows no `nope`).
- layering: the server with `--store` serves X alone; the hook binds X as its project layer and still
  layers/injects the profile beside it (open question 1).
- not followed: `--start` (the issue's suggested fix names it; the brief's property does not) and an
  abbreviated `--sto X` (open question 2).

## #172 — hook start-up cost

### Measured before (HEAD 4bab744 built into `$S/base`) and after (HEAD + this unit's cli.ts/hookadapter.ts in `$S/after`)

base/after back to back (`bash $S/timing.sh`, output `$S/timing.out`), load average 7.7-8.9 (siblings
building). Committed bench: `.shiftwork/notes-job67/J67-5-bench.mjs`, `J67-5-flag.mjs` (25-run flags).

| --mcp-report, empty HOME (25 runs) | 88 / 190 | 34 / 36 |

20-fact bed (`ALL=1 FACTS=20`), before -> after p50: UPS 96 -> 42, SessionStart 96 -> 43,
memory_save 93 -> 41, PreCompact 91 -> 39, PostCompact 90 -> 38, Stop 91 -> 40 (p95 86, the preview child).

the registered `bantamkit-mcp --hook` (which `--install-hooks` writes).

### What changed

cache. Python: no change (see open question 3).

## Open questions
1. Layering under an args pin: the server with `--store X` serves X alone; the hook binds X as its project
   layer but still layers the profile into UserPromptSubmit recall and injects the profile index at
   SessionStart. Should the hook switch layering off when the winning entry pins via `--store`? (Documented, not changed.)
2. `--start X` in a registration's args (the issue's suggested fix names it) and abbreviated `--sto X`
   are not followed. Separate issue?
3. The Python hook costs ~410 ms per call (10x Node): `bantamkit.mcpserver` imports `mcp`/`pydantic` at
   module level (~73% of its import time under `-X importtime`). Cutting it means restructuring
   mcpserver.py (J67-1's file this wave) or pointing the console script at a light dispatcher. Not done; documented.
4. A missing `--store` directory is designated by the server but refused (logged) by the hook's pin check,
   with a sentence that names BANTAMKIT_MEMORY_DIR because the args pin is fed through it. Acceptable?
