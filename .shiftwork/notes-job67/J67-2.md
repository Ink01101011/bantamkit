## 2. Per-tool reading (#182): what each handler writes, both runtimes

Rerun: `grep -n "log.record\|_record_raise\|_record_result" runtime-py/src/bantamkit/mcpserver.py`
and `grep -n "recordRaise\|recordResult\|log.record" runtime-ts/src/mcp/server.ts`.

**The event log decides `readOnlyHint`.** Every served handler appends a record to
`<store>/events/mcp.jsonl` when `BANTAMKIT_EVENT_LOG` is set (`log.record(...)` or
`_record_result`; `bantamkit_status` only through `_record_raise` on its raise path). With the
log OFF (the default; `EventLog.enabled` is `path is not None` / `path !== null`) those writes
do not happen. The brief: "when a tool writes a log line it is NOT read-only". So the hint
depends on the log's state, and the servers say so: the asset carries the log-off hints, and
`served_annotations` / `servedAnnotations` (one function per side) overlay
`EVENT_LOG_HINTS = {readOnlyHint: false, destructiveHint: false, idempotentHint: false}` on a
read-only tool when the log is on (append-only, and each call adds a line). The log is decided
once at startup in both runtimes, so `tools/list` is stable for a process.

| tool | writes with the log off (beyond the log) | hints in the asset |
|---|---|---|
| memory_save | the fact file + index (overwrites a same-named fact, resets `last_recalled`) | readOnly false, destructive true |
| memory_recall | `_stamp` rewrites `last_recalled` in each returned fact (`memory/store.py` `_stamp`/`_stamp_write`) — an in-place field rewrite, not additive, so no `destructiveHint: false` claimed | readOnly false |
| validate_json | nothing (pure) | readOnly true |
| shiftwork_clock_in | appends a brief line to `<checkpoint>.log.jsonl` (`shiftwork.py:_record_event`), never the checkpoint | readOnly false, destructive false (append-only), idempotent false (a line per call) |
| shiftwork_clock_out | rewrites the checkpoint (cursor, statuses, handoff), appends accounting/`uncommitted` lines | readOnly false, destructive true, idempotent false |
| shiftwork_status | nothing (`shiftwork.status`, "Never mutates"; Node `status`) | readOnly true |
| build_identity | nothing (hashes files it reads) | readOnly true |
| bantamkit_status | nothing (`status_report`, `degraded_conditions` read only) | readOnly true |
| memory_compact | archives facts out of the index (moves files) | readOnly false, destructive true |

## 8. Open questions

- Q1. **The event-log overlay is my reading of the brief's rule.** Strictly, every tool writes a
  log line when `BANTAMKIT_EVENT_LOG` is on, so a static `readOnlyHint` would have to be false
  on all 14 and hosts could auto-approve nothing. I made the hint follow the log's state
  instead (true only while nothing is written). If the user rules that the opt-in diagnostic
  log does not count, delete the overlay (`served_annotations` / `servedAnnotations`) and the
  two log-on literals; if they rule it counts statically, set the eight assets to false.
- Q2. `memory_recall` is `readOnlyHint: false` because `_stamp` rewrites `last_recalled`; the
  issue's "..." may have expected it read-only. `destructiveHint` is left at the default
  (true) there because a field rewrite is not "only additive".
