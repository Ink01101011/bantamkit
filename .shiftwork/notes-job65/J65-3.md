## 1. Parity, established by running both sides

The reference is `jsonschema 4.26.0` + `referencing 0.37.0` in the venv
(`.venv/bin/python -c "from importlib.metadata import version; print(version('jsonschema'), version('referencing'))"`).

**What python-jsonschema does per draft, measured** (`$S/py_drafts_probe.py`, and raw
`jsonschema.validate` with no bantamkit pre-scan in `$S/py_probe_raw.py` → `$S/py_raw.txt`):

- `validator_for` dispatches on `$schema` and the keyword table moves with it: draft-07
  `dependencies: {a: [b]}` on `{"a":1}` → `'b' is a dependency of 'a'`; under 2019-09 and
  2020-12 the same schema answers `(valid)` (the keyword is data there); draft-04 boolean
  `exclusiveMaximum` validates; draft-07 tuple `items` validates; `$ref` silences its
  siblings through draft 7 and not from 2019-09; `1.0` is an `integer` from draft 6 on.
- `$ref` into `#/$defs`, `#/definitions`, `#anchor`, `$dynamicRef`, `$recursiveRef` (2019-09)
  and `unevaluated*` all validate under every draft, with no base URI and no registry.
- A reference OUTSIDE the document (`https://…`, `other.json#/x`) raises
  `_WrappedReferencingError: Unresolvable` — LAZILY: the same reference in a branch the
  instance never reaches answers `(valid)`. A pointer to nowhere / unknown anchor raises
  `PointerToNowhere` / `NoSuchAnchor`, also lazily. An embedded `$id` resolves fine (it
  is a second resource `referencing` registers).
- Draft 3 (`http://json-schema.org/draft-03/schema#`) is validated by `Draft3Validator`.
- The `$schema` URI is normalised as `urlsplit(uri).geturl()`: with/without the empty `#`,
  upper-case scheme, leading space, empty `?` are one key; `https://` for draft-07, a
  trailing `/`, a non-empty fragment, an unknown URI → warn + latest draft (2020-12).
  Non-string `$schema` → `AttributeError`.

**The decision (written here as the brief asks):** the port DISPATCHES on `$schema` to
drafts 4, 6, 7, 2019-09 and 2020-12 with the reference's own keyword tables, and the two
runtimes jointly NARROW the reference library on three things, with one shared sentence
each, answered as `{valid:false, feedback}` rather than raised, so a model can act on it:

1. draft 3 anywhere in the document (the port has no draft-3 tables);
2. a `$ref`/`$dynamicRef` that is not fragment-only — EAGERLY, in document order, because
   the reference resolves it against a base URI the port does not model and cannot be made
   lazy about a remote it CAN resolve; refusing an unreached branch is the price;
3. an embedded `$id` (`id` under draft 4) beside any reference (a second resource).

A pointer to nowhere / unknown anchor stays lazy on both sides: `contract.py` catches the
`referencing` exception and prints the same sentence the port prints. None of this is a
divergence BETWEEN the runtimes — both say the same words — so there is no porting.md
divergence row; it is recorded in `docs/porting.md` (the `jsonschema` section) as a
narrowing of the reference.

**Side-by-side, 49 rows × 8 `$schema` columns = 696 (draft, schema, output) triples through
`schema_error` on both sides** (`$S/rows.json`; `.venv/bin/python $S/py_probe2.py $S/rows.json
> $S/py2.txt; node $S/node_probe2.mjs $S/rows.json > $S/node2.txt; sort each;
.venv/bin/python $S/classify.py $S/py2.sorted $S/node2.sorted`):

the suite — and all 64 are shapes the dialect's metaschema refuses (boolean
`exclusiveMaximum` outside draft 4, tuple `items` under 2020-12, a boolean subschema under
draft 4, …).

  and draft-07 tuple `items` validate instead of raising; draft 3 is refused by name on both
  sides, so no keyword is ever silently ignored for `valid:true`.

## 8. Open questions

1. `assets/tools/validate_json.json`'s description still says only "Validate candidate output
   text against a JSON Schema". It could name the supported drafts and the one-resource rule
   so a model does not send a remote `$ref` in the first place; left unchanged because the
   asset is shared by both runtimes and pinned by `runtime-py/tests/data/served-tool-surface.json`
   and the Node packaging test — a one-line change plus two fixture edits, orchestrator's call.
2. The eager refusal of a non-local `$ref` in an UNREACHED branch is a narrowing the raw
   reference does not make (it answers `valid`). Taken deliberately so the two runtimes agree
   (§1); if a user ever needs the lazy behaviour, both sides have to change together.
3. `validate_json` still lets `SchemaError`/`TypeError` escape as `isError` on both sides
   (porting.md reference-defect item 2, pre-existing, out of this ticket's scope).
