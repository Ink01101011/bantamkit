## 1. #131 — the dialect, decided by measurement

**Before** (the issue's run, reproduced by its verification unit; and at HEAD the suite's two
`ruling:` cases for `(?P<x>a)` and Thai `\d` were green, i.e. the sides differed): 5 of 5 probes disagreed (`^\d+$` on Thai digits, `^\w+$` on Thai letters, `^a$`
on `"a\n"`, `c\Z` on `"abcZ"` via the silent non-`u` fallback, `(?P<x>a)` raising on Node).

**Decision: the dialect is Python's `re`, on both runtimes.** The product's contract is the
reference's verdict (README: "CPython `jsonschema`'s error ordering"), so the port parses `re`'s
grammar (`translatePyPattern` in `runtime-ts/src/pyjsonschema.ts`, a port of `re._parser`'s
`_parse`/`_parse_sub`/`_escape`/`_class_escape`/`_parse_flags` validity rules) and emits a
`v`-mode RegExp whose constructs mean what they mean in `re`. The silent non-`u` fallback is gone.
Constructs with no faithful translation are REFUSED on both runtimes with one sentence
(answered, eagerly, before `check_schema`):

    the pattern '<repr>' is not supported: this validator refuses inline flags, look-behind,
    backreferences, atomic groups, possessive quantifiers, conditional groups and \N{...} escapes

Why each is refused, not translated: inline flags (case folding / verbose / dotall would need a
second translator; `(?u)` alone is the default and passes); look-behind (fixed-width in `re`,
any width in JS — the refusal BIT would differ); backreferences (a JS backreference to a group
that did not participate matches empty, `re`'s fails, and JS resets captures per iteration);
atomic/possessive/conditional (no JS syntax); `\N{...}` (no Unicode name table in the port, so
it cannot tell a defined name from an undefined one — refused BEFORE the parse on both sides).

Python finds them in `re._parser.parse(pattern)`'s tree (`contract._pattern_unsupported`); Node
marks them while parsing. A pattern `re` itself refuses is NOT refused by the pre-scan; it is
left to `check_schema`, which raises where it always raised (the words of that raise are the
existing `check_schema` ruling).

**Class equality, every codepoint** (`$S/py_classes.json`, `$S/cls_cmp.mjs`):

    .venv/bin/python -c "<dump \w \d \s membership for 0..0x10FFFF>"   # 3.12.13, unicodedata 15.0.0
    node $S/cls_cmp.mjs $S/py_classes.json                            # node v25.2.1, unicode 16.0
    # w py 137936 onlyPy 0 | onlyJs 5004 (1c89 1c8a a7cb … all Unicode-16 additions)
    # d py 680    onlyPy 0 | onlyJs 80   (10d40… Unicode-16 additions)
    # s py 29     onlyPy 0 | onlyJs 0

**Differential fuzz, 80,000 patterns** (`$S/fuzz_py.py N SEED OUT [valid]`, `$S/fuzz_node.mjs`):

    for s in 1 2; do .venv/bin/python $S/fuzz_py.py 20000 $s $S/fuzz$s.json && node $S/fuzz_node.mjs $S/fuzz$s.json; done
    for s in 3 4; do .venv/bin/python $S/fuzz_py.py 20000 $s $S/fuzzv$s.json valid && node $S/fuzz_node.mjs $S/fuzzv$s.json; done
    # each: 20000 patterns; 20000 agree; 0 disagree
    # (error/ok/unsupported: 15487/2451/2062, 15461/2473/2066, 12154/5322/2524, 12183/5229/2588)

Each row compares: refused-as-unsupported, refused-by-`re`, or the `re.search` bit over 36
strings (Thai, astral, `\x1c`, `﻿`, `\r`, `\x07`, `\x08`, `{`, …). The first run found one

closed by moving the `\N` check before the parse on both sides.

## 2. #132 — the budget

A document's patterns share **500 ms** (`PATTERN_BUDGET_MS`, both runtimes). Past it, one
sentence on both sides:

    the pattern '^(a+)+$' did not finish within the 500 ms this validator allows a document's
    patterns; rewrite it so it cannot backtrack catastrophically, as (a+)+$ does

- Node: `vm.Script('r.test(s)').runInContext(ctx, {timeout: remaining})` interrupts the RegExp
  engine itself (`$S/vm_probe.mjs`: interrupted after 303 ms for a 300 ms timeout; 41 µs per
  timed call vs 0.05 µs plain, `$S/vm_cost.mjs`). The event loop is blocked for at most the
  budget.
- Python: `re` holds the GIL for a whole search, so a worker thread does not help (measured:
  a 372 ms search in a thread, 1 main-thread tick, max gap 0.000 → the main loop never ran).
  Each search runs in a long-lived `python -I -S` child (`contract._PatternChild`), killed and
  replaced on timeout; spawn ~11 ms, not charged to the budget. `jsonschema`'s three modules
  that call `re.search` get a `_BoundedRe` shim that charges every search to the running
  validation's clock (a `ContextVar`), so `pattern`, `patternProperties`,
  `additionalProperties` and `unevaluatedProperties` are all bounded without re-implementing
  any keyword. Outside `schema_error` the shim is `re` itself.
- Ping proof, both servers, the issue's pattern (`'a'*40 + '!'`, `^(a+)+$`):
  `node --test runtime-ts/test/patterns.test.mjs` → `#132: a ping sent behind a catastrophic
  validate_json is answered within a second` (asserts ping < 1000 ms, validate answers the
  sentence); `.venv/bin/python -m pytest runtime-py/tests/test_contract_patterns.py -k ping`
  (same assertions; the Python ping returns immediately because the worker thread waits on a
  pipe with the GIL released).

Which side times out first on a BORDERLINE pattern is machine-dependent (stated in
`docs/porting.md`); the cases use a pattern that cannot finish on either.

## 3. #152 — a top-level scalar is a JSON document

`schema_error` now tries `json.loads(_unfenced(output))` (Node: `parseJson(unfenced(output))`)
first and falls back to `extract_json` only on a `ValueError`. `extract_json` itself is
unchanged (it is also the eval harness's and `JsonAnswerGate`'s parser; its callers expect a
dict or list). Before/after on the issue's probes: `"just a string"`/string, `1.0`/number,
`null`/null were `no JSON object found in output` on both; now `(valid)` on both. Prose with no
JSON (`42 is the answer`) is still the parse error; malformed JSON still carries the decoder's
text (the fallback's message, unchanged — `runtime-ts/test/contract.test.mjs`'s extract_json
tests pass untouched).

## 4. #153 — clipped feedback

`_clip(text, limit)` / `clipText`: at most `limit` CODEPOINTS, then `…(N more)`. In
`schema_error`: every `repr` of the error's instance in the message is clipped to 200, then the
whole detail to 1000 (bounds what a message quotes from PARTS of the instance, e.g. an
unexpected property's name), and `where` to 200. The issue's probe (1 MiB string,
`maxLength: 10`): feedback 1,048,672 chars → 262 chars on both:
`JSON does not match schema at 'x': 'yyy…(1048378 more) is too long`. The two refusal sentences
above clip the pattern's repr the same way.

## 11. Open questions

1. `\B` on the empty string follows CPython 3.11-3.13 (never matches); CPython 3.14 changed it
   to match. A Python 3.14 install of the reference would disagree with the port on exactly
   that input. Not refused, because refusing `\B` everywhere to cover one empty-string edge is a
   worse trade; flag for whoever moves the reference to 3.14.
2. Codepoints Unicode 16 assigned (5,004 letters/numbers, 80 digits) are `\w`/`\d` on Node 25
   and not on Python 3.12's Unicode 15. Both sides follow their own Unicode tables.
3. The Python reference now starts a `python -I -S` child the first time a validation searches
   a pattern. If `sys.executable` cannot be spawned (an embedded interpreter), `validate_json`
   raises. No such host is known; the alternative (searching in-process) is exactly #132.
4. `docs/mcp.md`:28 still describes feedback without the clip; not in this unit's files.
