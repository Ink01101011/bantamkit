## 2. What changed, and where the check lives

**#127 — the node's shape is checked at Layer 1, on both sides, before the graph is read.**
`workplan.py` gains `_shape_refusal` + `_is_integer`; `workplan.ts` gains `readNodes` +
`isInteger` and `plan()` now takes `readonly unknown[]` (the check that an element IS a
`PlanNode` is the planner's, not the caller's). `server.ts`'s `planNodes` no longer coerces:
it is `toJs(item)` plus the one thing it keeps reproducing on purpose, the reference's
`KeyError` for a node with no `id`. The pyargs `listDict` model is unchanged (`list[dict]`
still holds at the model, as pydantic's does). Four sentences, byte-identical both sides,
named by POSITION because the index is the one name every node has (string id or not,
duplicate or not):

    nodes[<i>] must be an object
    nodes[<i>].id must be a string
    nodes[<i>].depends_on must be a list of strings
    nodes[<i>].priority must be an integer

Order: shape of EVERY node (input order, then `id` / `depends_on` / `priority`), then the
three graph refusals as before. `integer` is JSON Schema's: `True` is refused (CPython's
`isinstance(True, int)` notwithstanding), `2.5` is refused, `3.0` is accepted — the port
cannot tell `3.0` from `3` once the value is a JS number, so the reference admits it too and
the two agree. NOT changed, because the surface pinned them before this unit and #127 does
not name them: absent or `null` `depends_on` is none, absent or `null` `priority` is 0
(`tool/missing-depends_on`, `tool/null-depends_on`, `tool/missing-priority`), and a node with
no `id` is still `Error executing tool work_plan: 'id'` (`tool/no-id`). See §7 Q1.

**Asset `work_plan.json`** reconciled to that: `depends_on` leaves the item's `required`
(it was advertised required and defaulted by both runtimes — the #133 class of mismatch in
the tool #127 is about), becomes `anyOf` array-of-string / null with "Optional: absent or
null means none", and the description names the fourth refusal. Golden
`runtime-py/tests/data/served-tool-surface.json` moved by hand on the 13 leaves
`test_the_served_surface_is_the_one_the_committed_golden_declares` printed.

## 7. Issues closed, and open questions

**#127 closed.** A node off the advertised item schema is refused `{result: "error", reason:
"nodes[<i>].<field> must be ..."}` on both runtimes, never coerced; the three inputs in the issue
are `tool/shape-*` cases in `workplan.mjs` and §3 shows them byte-identical.

**#133 closed on the brief's property (b).** Every advertised `minimum`/`maximum` on the served
roster is now either enforced like a wrong type (`skill_audit.usage` values, `skill_audit.budget`
ceiling), already refused by a handler (`skill_audit.budget` floor, `shiftwork_clock_out`
accounting), or removed from the schema with the clamp written into the description
(`memory_recall.k`, `memory_compact.reserve`); `k`'s description agrees with its schema; the
one `additionalProperties: false` (`handoff_patch`) was probed enforced.

Q1 (#127, pinned, not moved): a node with NO `id` still escapes as the raw `KeyError`
envelope `Error executing tool work_plan: 'id'` (`tool/no-id`), while a node with a non-string
`id` now gets the structured sentence. The issue did not name the missing-id case and the case
pins it on purpose, so it stayed; a follow-up could make it `nodes[<i>].id must be a string`
on both sides and amend `tool/no-id` — one line each in `planNodes` and `_shape_refusal`.

Q2 (#133, the `unitId` trap): the issue's "Expected" includes refusing an unknown top-level
key. No served schema advertises `additionalProperties: false` at the top level (`shiftwork_*`
advertise `true`; the rest omit it, which is `true`), and both runtimes ignore extras
(`wire` pins `extra: 1` accepted twice). Reconciling the other way — `extra="forbid"` on every
model, `additionalProperties: false` on every asset — is a surface-wide behaviour change
with host-compatibility exposure (the SDK's own `pre_parse_json` comment says Claude Desktop
sends arguments in shapes nobody asked for). Needs a user ruling; not done here. If ruled,
the Node side is one line in `validateArguments` plus the pydantic `extra_forbidden` frame
(`Extra inputs are not permitted`), measurable the same way §2 measured the bounds.

Q3 (docs, not in this unit's file list): `docs/shiftwork.md:489` and `docs/conformance.md`'s
`workplan` row still say three refusals / do not mention the shape check. One sentence each.

Q4 (one-sided arm not comparable at the core): `priority: 3.0` is accepted as 3 on both sides,
but the corpus cannot carry it (`JSON.stringify(3.0)` is `3`), so it is pinned per side in the
unit tests only. Over the wire the port's decoder keeps `3.0` as a float and `toJs` makes it
`3`; the reference's `json.loads` makes it `3.0` and `_is_integer` admits it — compared in
§3's fourth call (`{"id":"b","priority":3.0}`), same bytes.
