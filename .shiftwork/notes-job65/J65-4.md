## 2. What changed, and the one design choice

- **#166** — the allowed retry wrote `refused: false` back, re-arming the gate. Now a record
  whose signature matches keeps `refused: true`; the count still climbs; the log action for
  every later repeat is `allow-after-refuse-or-change` (the existing Python test pins
  `record, refuse, allow-after-refuse-or-change` for three reads and stays green). An edit
  (new mtime/size) writes a fresh record with `refused: false`, so it refuses once more.
- **#190** — `st.isFile()` / `stat.S_ISREG(st.st_mode)` after the stat; anything else returns
  exactly as a missing path does: no ledger entry, no log line, no refusal.
- **#167** — choice: **lock + temp-and-rename, same on both runtimes, file format unchanged**
  (`ledger-<session>.json` stays one JSON document, so every other arm, `inject-dedupe`'s
  ledger-shape case and the tests that `JSON.parse` the file are untouched). Append-only JSONL
  was rejected because `injected`, `saved` and `stopNudged` live in the same file and three
  other arms read-modify-write it; folding on read would have been a format change in four
  arms for a race measured in one. The lock is `<ledger>.lock` taken with `O_EXCL`
  (`fs.openSync(..., 'wx')` / `os.open(O_CREAT|O_EXCL)`), the only primitive both platforms
  (Windows included) and both runtimes share without a dependency; 5 ms poll, 2 s wait, a
  lock older than 10 s is a dead holder's and removed; on timeout the writer proceeds
  unlocked rather than fail the tool call. `writeLedger`/`_write_ledger` now write
  `<ledger>.<pid>.tmp` and rename, so a concurrent reader never sees a truncated file. Only
  the PreToolUse arm takes the lock (`updateLedger` / `_update_ledger`); see open questions.

## 6. Open questions

1. Only the `PreToolUse` arm takes the ledger lock. `UserPromptSubmit` (seen-set), the
   `memory_save` counter (`PostToolUse`) and `Stop` (`stopNudged`) still read-modify-write
   `ledger-<session>.json` unlocked; they now write through a rename (no torn reads), but a
   `PostToolUse memory_save` landing beside a parallel `Read` block can still lose one `saved`
   increment or one read entry. Those sections belong to J65-8/J65-12 per the brief, so the
   hunks were kept out of them; wrapping each in `updateLedger`/`_update_ledger` is a
   three-line change per arm when a unit owns those sections.
2. The lock has no case for the stale-holder path (a lock file older than 10 s is removed) or
   the 2 s timeout fall-through; both are exercised only by reading the code. A case would need
   a planted stale lock and a measured wait, which this unit judged out of scope for #167.
3. `docs/hooks.md` still says in its `tools/hooks` section that "There is no Python half of this
   adapter"; that sentence predates job62 and is not this unit's row. Reported, not edited.
