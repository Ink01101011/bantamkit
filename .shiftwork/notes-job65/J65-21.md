**#187 (shared).** `escape_ascii` (`runtime-py/src/bantamkit/mcpreport.py`) and `escapeAscii`
(`runtime-ts/src/mcpreport.ts`), applied to the four path-carrying arms of `host-log-root:` and
`event-log:` in both `render`s. Rule: every UTF-16 code unit outside printable ASCII
(0x20–0x7E) becomes `\uXXXX`, lowercase hex, one escape per code unit (an astral character is
its surrogate pair — Node gets that from `charCodeAt`, Python splits the code point by hand);
nothing else is touched, so a backslash — a Windows path — reads as typed. Not `json.dumps`
(escapes `\` and `"`), not `ascii()` (`\U0001f600`). The doc's "ASCII" contract now says so
(`docs/mcpreport.md`, "ASCII includes the two paths"), so the second arm of property (b) — a
doc exemption — was not taken. Same bytes both sides:

    .venv/bin/python -c "from bantamkit.mcpreport import escape_ascii as e; print(repr(e('a/แ😀\\\\b\n\x7f~ ')))"
    node --input-type=module -e "const {escapeAscii:e}=await import('./runtime-ts/dist/mcpreport.js');console.log(JSON.stringify(e('a/แ😀\\\\b\n\x7f~ ')))"
    # both: a/แ😀\b\u000a\u007f~

## 7. Open questions

1. The escape is per UTF-16 code unit (`😀` for 😀). If a reader ever wants the
   paths back, that is JSON's spelling minus the `\\`/`"` escapes — fine for a human, lossy only
   for a path that literally contains the six characters `แ`. No issue asked for a
   round-trip; flagging the choice, not asking for a change.
2. The `busy-130k` bed adds ~2.5 s and 32 MB of scratch to every `--suite mcpreport` / `--all`
   run (Python 1.4 s + Node 0.5 s + the write). It is above V8's spread limit on purpose; a
   smaller bed would be green against the defect. If the harness's wall time becomes a concern,
   the number to keep is ≥ ~125k, not the 130k.
3. `--all` could not be shown at 0 failures from this unit because of the J65-19 surface above;
   re-derive after its commit.
