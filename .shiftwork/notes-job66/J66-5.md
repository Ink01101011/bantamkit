## What changed

**(a) #124: one JSON document when degraded, in both runtimes.** There is a new helper in each
server: `notedJson` in `runtime-ts/src/mcp/server.ts` and `_noted_json` in
`runtime-py/src/bantamkit/mcpserver.py`. They sit beside `noted`/`notedDict`. The success
returns of `skill_audit` and `token_ledger` now call it in place of `noted`. The helper
splices `,\n  "bantamkit_degraded": <json string>` in before the document's closing `\n}`. It
does not re-parse the document, so every byte before the key is the healthy reply's. That
also means `JSON.parse` never touches a token count near 2**53. The key's value is the same
footer string the structured tools carry, and the key always comes last. `as_json`/`asJson`
always serialise a non-empty dict at indent 2, so the document always ends `\n}`. The
refusals (`toolFailed`) are prose, so they keep the prose footer. docs/status.md *The footer*
now lists the two tools as a third shape, "JSON-document replies". docs/skill-audit.md and
docs/ledger.md say the reply always parses. The tool assets are unchanged:
`assets/tools/*.json` is not in this unit's file list, and the descriptions still say "one
JSON document", which is now true.

**(b) #150: BOM. Decision: report it as unparsed on both runtimes.** The other choice was to
tolerate it on both. It was not taken, for four reasons:
- The reference already reported the BOM as unparsed.
- The host never writes a BOM, and RFC 8259 says a JSON text must not add one. A line that
  carries one is not the host's line, and an omission is what names that.
- `JSON.parse` and `json.loads` already reject a BOM on line 2 or later. Tolerating it only on
  line 1 would keep the special case that caused this.
- `lines == requests + omissions` stays visible.

The only change is in Node: `TextDecoder('utf-8', { fatal: true, ignoreBOM: true })` in
`readUtf8Strict`, so the BOM reaches `JSON.parse`. Python only gained a docstring bullet. The
conformance case and the unit tests go red under the other choice (mutation m150 below:
`utf-8-sig` plus the default decoder).

**(c) #151: symlink loops.** A symlinked DIRECTORY is neither walked nor read. Node checks
`lstatSync(child).isSymbolicLink()` in the directory arm. Python checks
`child.is_symlink() or _is_junction(child)`. The junction check exists because Node's lstat
calls a Windows junction a symlink, and `Path.is_junction` only exists on Python 3.12+. This
is `skill_audit`'s rule (`followlinks=False`). A symlink to a transcript FILE is still read,
because it cannot loop. The time is bounded by construction: the walk is linear in the real
tree. On the issue's fixture the answer is 1 transcript in milliseconds (probe above), down
from 33 at ELOOP.

## Conformance cases, and the mutation that turned each red

Every mutation ran on a fresh rsync copy of the tree, never in place. The runner is
`$SCRATCH/J66-5/mutate.sh <name>`: it rsyncs the tree, applies the sed, runs `tsc`, then runs
`node tools/conformance/run.mjs --suite tokenledger --suite wire`.

New cases:
- `tokenledger`: the read differentials `read: a BOM before the first record (#150)` and
  `read: a directory symlink loop and a file symlink (#151)`, plus `walk: a directory symlink
  loop (#151)`. There are per-side literals for each property (`... — python` and
  `... — node`).
- `wire`: sessions `j66-5-json-healthy` and `j66-5-json-degraded`. They use the same one-byte
  straddle as `status-*` (a 46-byte index at budget 52 and 51). Every frame is compared, and
  `j66-5: the reference|the port keeps skill_audit and token_ledger ONE JSON document when
  degraded (#124)` pins the property per side. The degraded reply parses, its last key is
  `bantamkit_degraded` carrying the footer, `structuredContent.result` equals the text, the
  healthy reply has no key, the healthy bytes are the degraded reply's prefix, and the
  refusal is prose followed by the footer.
