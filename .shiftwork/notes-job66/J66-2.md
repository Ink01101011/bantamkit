## #171: the stale-install line printed a bare `node`

**Reproduced before the fix** (the issue's repro, adapted to `runtime-ts/dist`, kept install's
`cli.js` replaced by an argv-reporting stub so nothing updates):
`node .shiftwork/notes-job66/J66-2-probe171.mjs`. At 68119d1 the printed command was
`node "<H>/.bantamkit/mcp/node_modules/bantamkit-mcp/dist/cli.js" --update`, and
`/bin/sh -c` with `PATH=/usr/bin:/bin` gave exit 127. The job64 test
(`tools/hooks/update-signal.test.mjs`, *the stale line prints a command that runs from a shell
with no bantamkit on PATH*) passed anyway because it put `dirname(process.execPath)` on PATH.

**After:**

    run via /bin/sh with PATH=/usr/bin:/bin -> exit 0 "[\"--update\"]"

Changes:
- `runtime-ts/src/hookadapter.ts`: `UPDATE_LINE` prints `` `"{node}" "{cli}" --update` `` and
  `{node}` is `process.execPath`, which is the node the hook registration launched. Python
  has no counterpart: the reference emits no stale-install line (`updateProbe: "node-only"`,
  porting.md row *the hook's stale-install line*; J65-0 parity table). That row's text
  `bantamkit-mcp --update` had been stale since 2026-09-26. It is amended to the
  absolute command.
- `UPDATE_LINE_MAX` went from 500 to 1024. **Measured:** the conformance bed's home is a long
  `$TMPDIR` path, which pushed the line past 500 bytes, so the printed command was cut before
  its closing backtick. The first run of the new case was red because of this
  (`$S/hooks1.txt`: argv null, startsWithExecPath false). The line carries three absolute
  paths now, and a cut line is a cut command.
- The job64 test's PATH is `/usr/bin:/bin` now, which strengthens it. Its `expectedLine`
  literal names `"${process.execPath}"`.

**The status sentence (both runtimes), fixed the same way, as the brief requires.**
`updatecheck.UPDATE_AVAILABLE` used to say `` `{program} --update` ``. The template now says
`` `{command}` `` and is still byte-identical on both sides. Each runtime fills `{command}`
with its own interpreter:
- reference: `update_command()` = `"<sys.executable>" -m bantamkit.mcpserver --update`
- port: `updateCommand()` = `"<process.execPath>" "<dist/cli.js>" --update`

`decide` / `update_status` / `update_line` (and the camelCase versions) take an optional
trailing `command`. The default is the function above. This difference is deliberate, so it
gets a new `docs/porting.md` row (*the update command `bantamkit_status` prints*) and a
`ruling:` case. It is not a refusal, so it has no refusal-bit companion. Its companions are
three per-side literals: the exact command, the quoted absolute interpreter, and the command
run from `/bin/sh` with `PATH=/usr/bin:/bin` with `-h` swapped in for `--update`, so nothing
reaches a registry. Every rendered line is compared with each side's own command masked to
`<command>`. `docs/status.md`'s sentence row and `docs/hooks.md` are updated.

## #173: Python `--hook`, `--statusline`, `--mcp-report` needed the [mcp] extra

Proved in a real venv without the extra:
`python3 -m venv $S/nomcp && $S/nomcp/bin/pip install -e runtime-py`. It has no `mcp` and no
`pydantic` (`nomcp/bin/python -c "import mcp"` gives ModuleNotFoundError). The probe runs
under `HOME=$S/home`:

    echo '{"hook_event_name":"PostCompact","session_id":"x","cwd":"'$S/proj'"}' | HOME=$S/home $S/nomcp/bin/python -I -m bantamkit.mcpserver --hook; echo $?
    echo '{}' | HOME=$S/home $S/nomcp/bin/python -I -m bantamkit.mcpserver --statusline; echo $?
    HOME=$S/home $S/nomcp/bin/python -I -m bantamkit.mcpserver --mcp-report </dev/null; echo $?

Before the fix, all three printed `bantamkit-mcp needs the MCP extra: pip install
"bantamkit[mcp]"` and exited 1. After it, all three exit 0: SessionStart injects the
toolbox block, statusline prints `bantamkit Unknown ⚪ · event log off`, and mcp-report prints
`bantamkit mcp report v1`. The bare server (`</dev/null`) still exits 1 with the hint, and
`--assets-root` exits 0 and prints the assets path.

Change in `mcpserver.py main()`: the SDK check moved after `_parse_args()`. It is skipped
when `args.assets_root or args.hook or args.mcp_report or args.statusline`. Those arms return
from `_dispatch` before any server exists. `--assets-root` is included because it precedes
`--hook` in dispatch and needs no SDK. Side effect: `-h` without the extra now prints help
instead of the hint, because argparse exits during the parse. No test pinned the old order
(`grep -rn _INSTALL_HINT runtime-py/tests tools/conformance` is empty). Node has no extra, so
that side was already right.

Gates:
- `--suite hooks` block `no-mcp-extra`: the reference runs with `sys.modules['mcp'] =
  sys.modules['pydantic'] = None` via `runpy`, and the port runs as is. Cases are the per-side
  literal `{exit: 0, hint: false}` for each flag, the side-to-side differential, and a CONTROL
  pinning that the crippled reference still refuses a bare server (`{exit: 1, hint: true}`),
  so the block cannot pass on a reference that quietly kept the SDK.
- pytest `test_hookadapter.py::test_the_host_registered_arms_run_without_the_mcp_extra[3 flags]`,
  with the same control.

## Open questions

1. PowerShell: a quoted first word is a string expression, so the printed command needs `& `
   in front there. sh, bash, zsh and cmd run it as printed. The old bare `node "<cli>"` did
   run in PowerShell. The hook text is read by the model, which runs it through Bash (Git Bash
   on Windows), so I left it and documented it in docs/hooks.md. Should win32 get a `& `-free
   form instead?
2. `--update` and `--install*` still require the extra on Python, for example `--update`
   from a plain install. That is outside #173's three flags and was left alone.
3. `bantamkit_status` builds its command from the running process. A server launched from an
   npx cache therefore prints the npx-cache `cli.js`, which is the install that answered, as
   the sentence claims.
