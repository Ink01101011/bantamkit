## 2. What changed (Node only)

**`runtime-ts/src/mcp/server.ts`**
- `guardRequests(server, wire)`, run at the end of `buildServer`: wraps every entry of the SDK's
  handler table (`Protocol._requestHandlers`, TS-private; the only place that also holds the
  SDK-registered `initialize` and `ping`). Before a handler runs: (1) a `null` top-level param is
  dropped (pydantic `X | None = None`; a required field is still refused once its null is gone);
  (2) the method's own SDK schema is checked first, refusal -> `rpcError(-32602, 'Invalid request
  parameters', '')` — byte-identical to the reference; (3) the init gate: `initialize` opens it
  synchronously once its params validate, anything but `ping` before that is the same `-32602`.
  A missing table, or a served method with no schema in `REQUEST_SCHEMAS`, throws at startup.
- `templateName(uri, prefix)` replaces the two `[^/]*` regexes in `resources/read`: the
  reference's match + unquote + security policy (above). The rubric path is joined as text, not
  `path.join`, so `x%2F..%2Fcode-quality` is not folded lexically into a hit the reference misses.
- `argumentsFrom`: `arguments: null` is an empty dict (pydantic reads it as absent).

**`runtime-ts/src/mcp/transport.ts`** (J66-3's file; one local hunk in `consume` + two helpers)
- The TS envelope schema checks a request's `params._meta`; the reference's envelope takes any
  object and checks `_meta` per method. So `_meta: 5` was `-32600` with `id: null` on Node and
  `-32602` under the client id on Python; `_meta: null` / `progressToken: true` were refused on
  Node and served on Python. Now: a REQUEST the envelope refuses is retried with `_meta` set
  aside; if that passes, it travels on without `_meta`, flagged `paramsRefused` when the
  reference's `RequestParamsMeta | None` (lax) would refuse it (`referenceTakesMeta`), and the
  guard answers it `-32602`. Notifications are untouched (see open question 2).

**Conformance (`tools/conformance/suites/wire.mjs`)**: five sessions, compared by the per-id
loop (canonical + raw bytes) AND pinned per side against literals in a new `j66-4:` block:
`j66-4-params` (20 refused params + 5 null-optional/lax-`_meta` served), `j66-4-preinit`
(7 served methods before `initialize`, ping, then a served call), `j66-4-initbad` (a refused
`initialize` opens nothing), `j66-4-init-burst` (`initialize` + call in ONE write: call served),
`j66-4-resources` (14 unknown URIs, 7 matched-but-absent, `%6Demory` served).
`wire_ref.py` needed nothing (J66-3's `burst` directive suffices).

**Amended pin (COMMON: an issue outranks a pin that contradicts it).** The `bad-params` session
was RULED ("SDK lineage ... the port has no seam ... TS SDK says `Invalid tools/call request:
<zod issue list>`"), and listed in `RULED_SESSIONS`. Its text was already stale at 02f6fdf (the
port said `-32603`, measured above), and #147 is exactly the behaviour it pinned. With the seam
found the two sides agree, so a ruling would go red as stale: the case is now an UNRULED equality
case citing #147, and `bad-params` is compared verbatim by the per-id loop. Old contract and the
reason are in the case comment.

Docs: `docs/mcp.md` *The frames themselves* gains three bullets (params, before initialize,
resources/read). No `docs/porting.md` row: no deliberate difference was introduced (one ruling
was removed).

Tests: `runtime-ts/test/request-guard.test.mjs` (6, buildServer over the real transport on
in-memory streams), `runtime-py/tests/test_mcp_request_guard.py` (3, the reference over stdio).

Pre-existing (J66-3's envelope path); this unit's `_meta` retry covers REQUESTS only. Probe: `node scratchpad/one.mjs <side> '<that line>'` (the same frames via `J66-4-probe.mjs edges` shape).
3. **`prompts/get` with an unknown name**: reference `{"code":0,"message":"Unknown prompt: x"}`, port `-32602` with `data: null`. Pre-existing, unruled, outside #147/#178/#180; `runtime-ts/test/server.test.mjs:1485` pins the port's `-32602` ON PURPOSE, so it is a question, not an edit. Probe: `PROBE_FULL=1 node .shiftwork/notes-job66/J66-4-probe.mjs <side> edges` id 312.
4. **The `unknown-methods` ruling** says the TS SDK has "no seam" to add `data: "<method>"` to `-32601`. `Protocol.fallbackRequestHandler` is a public seam; not touched (outside scope).
5. A spec method the server does NOT serve (`logging/setLevel`, `completion/complete`) with invalid params: the reference validates first (`-32602`), the port says `-32601`. Not probed against the wire suite; follows from reading `runner.py`.
