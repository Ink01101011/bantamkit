## 4. Finding, BLOCKER B1 (#118): a CR-only host file is re-indented differently by the two runtimes

`_detected_indent` (Python) reads with `Path.read_text`, which is universal-newline, so a lone `\r` is
a line break. `detectedIndent` (Node) splits a `readFileSync` string on `\n` only. On a host file
whose lines end in a bare `\r` (JSON allows `\r` as whitespace, and the file parses on both sides),
Python detects 4 spaces and writes 4. Node sees one line, falls back to 2, and writes 2. So the two
runtimes write DIFFERENT bytes, and Node drops the file's own indent, which is the property #118
promises on both counts. Probe (6 seeds: CR, CRLF, space+tab, BOM, blank lines, one-line):

    bash $S/indent-probe.sh "$PWD"     # script reproduced in section 7
    -> DIFF exit=0/0 seed={\r    "mcpServers": {}\r}\r
         py line2: 4 spaces + "mcpServers"   nd line2: 2 spaces + "mcpServers"
       SAME for the other five seeds (BOM: both exit 1).

The `install` suite stays green because no case seeds a CR-only file. The fix belongs to J66-13: make
Node split on `\r\n|\r|\n` (or Python read with `newline=""` and split the same way). Both runtimes
must land the same rule. Add a seed with bare-`\r` line endings to `install-host-text`, with a
per-side literal, and give the mutation count. Narrow (classic-Mac line endings), but it is a parity
defect introduced by this job's #118 fix, in the 0.35.9 set. #118 is REOPENED with this comment.
