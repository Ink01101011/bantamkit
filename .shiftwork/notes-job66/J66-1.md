## #145 — asset loaders read outside the pack

Shared defect (J65-0 row 145): `assets.py` joined the name verbatim too. Both runtimes now route
every loader through one helper (`assets.ts::assetPath`, `assets.py::_asset_path`): a name with
`/`, `\`, `:`, NUL, or `..` anywhere is refused BEFORE any filesystem access, and the joined path
is then checked LEXICALLY (`path.resolve` / `os.path.abspath`, not realpath — a pack may be a
symlink farm) to sit directly in `<root>/<kind>s/`. The refusal is `AssetNotFound` with ONE
sentence on both sides: `<kind> asset name is not a bare name: <name>` (kind = tool | schema |
skill). Being an `AssetNotFound`, the MCP resource handler's `unknown skill asset: <name>` answer
is unchanged on both servers. The not-found sentence (`<kind> asset not found: <path>`) is
unchanged for a bare name. The colon is refused because on Windows `Path("tools") / "C:x"` is
drive-relative and leaves the pack, while Node's `join` keeps it inside: refusing it keeps the
two runtimes on one answer.

Repro from the issue, adapted to the built dist and the venv (throwaway HOME asserted):
