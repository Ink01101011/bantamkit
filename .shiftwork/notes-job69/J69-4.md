# J69-4 — Task 4: the usage ledger, the hook log and the event log onto `LogSegment`

Branch `feat/199-recall-by-meaning`, shared tree with J69-2 (HotIndex, uncommitted). `SP` is this unit's scratchpad,
`$S`.

## Files

- `storage/logsegment` (both): additive API: lock timing per instance (`wait_ms`/`stale_ms`/`poll_ms`, Node
  `ExclusiveOptions`); `.size`, which is the live file's size right after the last successful `append`, or -1;
  `fold_lines(older_than | None, reducer(pairs) -> lines)`, which is `fold` for a reducer that writes lines as
  read. `fold` itself is unchanged and now runs through the same private core.
- `memory/usage` (both): reads, appends and the fold go through `LogSegment`. The fold is
  `seg.fold_lines(None, reducer)`, and J68-4's fold body is that reducer, kept byte for byte. A new argument,
  `rotate_bytes` (Node: `rotateBytes`), is added. When it is None, Python reads `logsegment.ROTATE_BYTES` at call
  time.
- `hookadapter` (both): `_log`/`log` is `LogSegment(run.log).append(...)`, then `rotate(ROTATE_BYTES)` when
  `seg.size > ROTATE_BYTES`. hookadapter's private copy of the ledger-lock loop (`_update_ledger`/`updateLedger`)
  now calls `storage.lock.exclusive` with its own `_LEDGER_LOCK_*` values. J69-1 handed this over (deviation 8).
- `eventlog` (both): records are appended through `LogSegment.append`. The rotation stays the event log's own (see D1).
- Tests: `runtime-py/tests/test_storage_log_consumers.py` (14 tests), `runtime-ts/test/storage-log-consumers.test.mjs`
  (13 tests).
- Conformance: `storage-log.mjs` gains 4 scenarios at the END plus a ruling and literals, and `storage_ref.py` gains
  the matching ops in its storage-log section. `recall-usage.mjs` and `usage_ref.py` gain a `rotate` scenario, a
  `gz` op and a literal. `hooks.mjs` gains the `hook-log-rotate` block.
- Docs: `docs/porting.md` (a divergence row for the ruling), `docs/conformance.md` (an amendment to the storage-log
  row), `docs/eventlog.md` (the append path; rotation kept), `docs/hooks.md` (the hook log rotates into `.gz`).

## Deviations from the plan (code wins, the property is kept)

- **D1. The event log does NOT rotate into `.1.gz`.** Plan Step 1 says each of the three logs rotates to
  `<name>.1.gz`. The event log has a documented cross-runtime rotation contract (`docs/eventlog.md`: one plain
  `<path>.1`, never a `.2`, a 2 MiB ceiling). Three things read or pin that contract:
  - `--statusline` and `--mcp-report` read `mcp.jsonl.1` as plain JSONL in both runtimes;
  - `test_eventlog.py` and `eventlog.test.mjs` pin it;
  - `docs/eventlog.md` §"Stream 2" rules that one rotation rule cannot be right for both this log and the hook log.

  Switching to `.gz` would have meant changing two readers in each runtime and rewriting existing tests, which is
  forbidden. It would also make a bounded log unbounded until Task 6 lands. So the event log appends through
  `LogSegment.append`, which gives it the lock, the cut-line repair and the same bytes, and keeps its own rename to
  `.1`. Its "rotate case" is the new `storage-log` event-log scenario, which pins the plain `.1` per side.
- **D2. The rotate trigger is the append's own size, not "every 100th append".** A hook is a fresh process for
  each event, so an append counter cannot persist without a second file. Instead `append` records `.size` from the
  seek or fstat it already did, and the appender calls `rotate` only when `size > ROTATE_BYTES`. That keeps the
  plan's property (no extra `stat`) and makes the boundary deterministic.
- **D3. `fold_lines` was added to `LogSegment`.** The plan says usage's fold "becomes the reducer that
  `LogSegment.fold` calls". Using `fold` as written would change the ledger bytes in two ways:
  - it serialises the reducer's rows with `dumps_line`, so the folded weight would lose its 9-decimal spelling;
  - it hands the reducer dicts, not lines, so the latest save could not be kept as read (CRLF, `1.0`, decoded
    invalid UTF-8).

  `recall-usage` would have gone red. `fold_lines` gives the reducer `(row, line)` pairs and writes the lines it
  returns verbatim. With `older_than=None` it folds the whole live file and rewrites even when nothing is old, which
  is J68-4's fold. `recall-usage` stayed 167/0 byte-identical before any new case was added.
- **D4. Python's hook-log line is binary LF now.** Before, `_log` opened the file in text mode, which writes CRLF
  on Windows. It also used a `json.dumps` that raised `UnicodeEncodeError` on a lone surrogate (from an
  `os.fsdecode` path, say), which is not an `OSError`. That error escaped `_log`. Through `LogSegment` the line is
  binary LF and the surrogate is escaped as `JSON.stringify` does. A NaN in a record is now dropped by both sides;
  before, Python wrote `NaN` and Node wrote `null`. No hook record carries a float today.
- **D5. Usage's auto-fold no longer runs under the append's lock.** The append and the fold each take the lock in
  turn. An `OSError` inside the auto-fold now leaves `append` answering True on Python, because the event *was*
  written; before, it answered False. A `ts` the fold cannot parse still raises on Python and still answers
  `false` on Node, as before.
- **D6. `read(since)` (J69-1 open item 1) was NOT built.** No Task 4 consumer needs it. It is left for Task 6
  (Retention), whose folding reads by age.

## J69-1 open item 3: the byte divergence of floats and integer-like keys

**Decision: pin it, do not normalise it.** The Node side cannot recover `1.0` after JavaScript has parsed it. So
the only possible normal form is Python emulating `Number.prototype.toString` and V8's key order inside
`dumps_line`. That is a third serialiser to keep true, for input that none of the three logs produces from its own
code:

- usage writes strings, and spells its own weight `.9f`;
- the hook log writes ints, strings, bools and lists;
- the event log writes closed-set tokens, ints and bools.

The only way in is a host-echoed hook field (`session`, `source`), and that field diverged the same way before #204.

What pins it, in `storage-log`:

- a `ruling:` case on the bytes of `{"b":1,"1":2,"f":1.0,"e":1e-7,"ts":"n"}`, which each side builds in code
  (a JSON payload cannot carry `1.0`);
- a non-ruled `read` beside it (the values agree);
- `LITERAL: the reference spells …` (`{"b":1,"1":2,"f":1.0,"e":1e-07,"ts":"n"}`);
- `LITERAL: the port spells …` (`{"1":2,"b":1,"f":1,"e":1e-7,"ts":"n"}`);
- a row in the `docs/porting.md` divergence table.
