# J72-12 — probe B: session-context query expansion, BM25 only (implementer claude-opus-5-5)

VERDICT: **refuted at the lower bound, and very unlikely at any plausible label rate.** No variant meets the bar shape on
dev (p >= p(B) + 0.05 AND r@3 >= r@3(B) + 0.01), and no variant passes a single bootstrap resample (0/5 for all eight).
Every variant LOWERS p@inject. Only the down-weighted B4 (λ 0.25) keeps r@3 (+0.006), and it still falls short of the
+0.01 margin. The hypothesis "the earlier prompts fix the topic" does not hold on the judge-labelled dev set. Adding the
previous prompt pulls in facts about the *earlier* topic, and the judge labels relevance to the *current* prompt, which
is how gold is labelled.

Read-only on product code. **No gold look**: gold was not read, and `gold-looks.jsonl` was not touched. No ollama call.
Tracked: this note and `J72-12-scripts/` (prev.py, expand.py, targets12.py, offsets.py, lat_prev.mjs). None of them holds
prompt, fact or label text. Untracked and private: `cache/J72-12-prev.jsonl`, `cache/J72-12-results.json`,
`J72-12-unjudged.jsonl`, `J72-12-judge-targets.q{1,2,3}.jsonl`.

## 2–3. Variants and the dev table
`cd $S && $R/.venv/bin/python $P/J72-12-scripts/expand.py $P $S $P/cache/J72-12` (about 9 s)
- **BM25 path.** Every score vector comes from the product's own `_pooled` walk, with J72-5 dev_extract.py's recording
  scorer and the walk unchanged. View B is `lib.ordered(s, w, s > 0)` top 3, as J72-5 checked it. `GATE_RATIO` and
  `GATE_FLOOR` are 0, so `rank_columns` admits exactly s > 0.
- **Asserted on every run:**
  - The plain-prompt scores and weights equal `cache/dev-rows.json` bit for bit.
  - B top 3 == product `inject_candidates` on 60/60.
  - For B1 and B2, the harness top 3 == product `inject_candidates(expanded query)` on **60/60 each**.
- **Query construction.** Each previous prompt is cut to 500 chars, and the parts are joined with "\n", older first. B3
  is B1 when `len(prompt) < 80`, else B.
- **B4.** The product BM25 has no per-query weight, so the harness builds it. The product walk is run twice, once on the
  prompt and once on the joined previous k prompts. The two raw BM25F score vectors are combined as
  `s = s(prompt) + λ·s(prev)`. The product's layer weights are kept, and the result is ranked by `lib.ordered(s, w, s > 0)`.
  A prompt with no previous prompt gets `s(prev) = 0`. The grid is k ∈ {1, 2} × λ ∈ {0.25, 0.5}.
- **Labels and metrics.** Labels are `dev-labels-merged.jsonl` (100 positives, 929 judged), and metrics are `lib.metrics`.
  An unjudged pair counts as negative. The "upper" columns score every unjudged injected pair as positive, for
  information only.
- **Bootstrap.** J72-10's: `random.Random(20261023)`, `choices(sorted ids, k=60)` × 5, with B rescored on each resample.
  `boot_metrics` is copied from devsearch10.py. B's resample numbers equal J72-10's: p .2331/.2378/.3218/.3289/.2342 and
  r@3 .4350/.4167/.4970/.4242/.4167.

## 4. Feasibility: where the product would get the previous prompt
- **`transcript_path` in the UserPromptSubmit payload.** Claude Code sends it, and the product already reads it:
  `HookInput.transcript_path` (runtime-ts/src/hookadapter.ts:199). `resolveNativeMemory` uses it for branch 3, and the
  ledger keys `injected` by it. No new host surface is needed.
  - Cost probe:
    `python3 -I $P/J72-12-scripts/offsets.py ~/.claude/projects $P $S/offsets.jsonl && node $P/J72-12-scripts/lat_prev.mjs $S/offsets.jsonl`
  - Method: for each dev prompt, the transcript is cut at that prompt's record, which is the hook-time end of the file.
    It is read backwards in 64 KiB chunks until the previous k prompts that pass the test are found.
  - It finds exactly J72-12-prev's prompts on **60/60**.
  - Warm page cache, Node v25.2.1, read and parse only: **k=1 p50 0.23 ms**, p90 7.7 ms, max 29 ms. **k=2 p50 0.74 ms**,
    p90 7.8 ms, max 220 ms (one turn carries 16 MB of tool output between two prompts).
  - Bytes read for k=2: p50 512 KiB, p90 2.4 MB, max 15.9 MB. The transcripts themselves are p50 1.6 MB, max 26 MB.
  - Estimated hook p50 rise: under 1 ms, plus a second BM25 pass for B4. The tail is unbounded unless the read is capped.
    A product version would need a byte cap, for example 1 MB, and to give up when it hits it.
  - Cold-cache cost was not measured.
- **A per-session ring under `~/.bantamkit/hooks/`** inside the existing ledger. `readLedger`/`writeLedger` already run on
  the injection path. The extra I/O is about 0, but the `none` and `no-headers` return paths would also have to write.
  It would put prompt text on disk in bantamkit's own state. The hook's privacy rule (`promptFingerprint`: "nothing
  reconstructible goes in") forbids that for the log and argues against it here, so it needs a user ruling.
- **Touch graph.** It holds file touches (`touchContext`, `W_CONTEXT`), not prompts. It cannot supply the previous
  prompt. It already gives a session-topic signal of a different kind.
- Moot for now, because the variants fail on dev. Both runtimes would also need the same change plus a conformance case,
  and none is proposed.
